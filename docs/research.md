## Verified Obsidian APIs (`obsidian.d.ts` 1.14.4)

- `registerView(type, (leaf) => View)` and `registerExtensions(['notebook'], type)` (extensions without the dot).
- `FileView` (`file: TFile | null`, `allowNoFile`, `onLoadFile(file)`, `onUnloadFile(file)`, `getDisplayText()`, `canAcceptExtension(ext)`). `TextFileView` adds `data`, `requestSave` (2 s debounce documented, internal logic not inspectable), `save()`, `getViewData()`/`setViewData(data, clear)`; reloading on external modification is not documented in the `.d.ts`.
- `vault.create`, `vault.createFolder` (throws if it exists), `vault.read` (to be used for read-modify-write, not `cachedRead`), `vault.modify`, `vault.process(file, fn)` (atomic, synchronous `fn`, since 1.1.0), `vault.getFileByPath`/`getFolderByPath` (since 1.5.7), `normalizePath`, `vault.on('modify' | 'delete' | 'rename')`.
- `Platform.isMobile`, `Platform.isAndroidApp`; `addRibbonIcon`, `addCommand`, `PluginSettingTab`, `loadData`/`saveData`, `registerDomEvent`, `registerEvent`.
- Since 1.7.2 tabs are "deferred": `leaf.view` may not be instantiated yet.
- `workspace.on('quit')` is "best effort" and unreliable on mobile: saving cannot rely on it → flush on `visibilitychange` (hidden) and `pagehide`.
- Mobile: no Node/Electron modules (crash), regex lookbehind only on iOS ≥ 16.4, Android debugging with `chrome://inspect`.

## Consequences for M1

1. **View**: `FileView` (not `TextFileView`) to have full control over saving: serialize → re-validate → write with `vault.process`, and never write if the file was not readable. `TextFileView` would write whatever `getViewData()` returns, with internal logic that cannot be verified.
2. **Stroke shape**: perfect-freehand as the only runtime dependency (MIT).
3. **Format**: versioned JSON with a custom extension (see `docs/architecture.md`).
4. **Licenses**: no GPL/AGPL/CC-NC code copied. The ideas taken from Excalidraw, Handwriting, Saber and Butterfly were reimplemented from scratch.

## Conflicted copies made by sync clients (#122)

Date: 2026-10-29. Web search of vendor pages, university IT pages and forum reports; no code copied. Vendors document the behaviour (both versions are kept, one gets another name in the same folder) more clearly than the exact name, which varies by client, version and OS. Patterns recognised by `src/storage/conflicts.ts`:

| Client | Name of the conflicted copy | Confidence |
|---|---|---|
| OneDrive (Windows) | `Name-<COMPUTERNAME>.ext`, also with a counter (`-1`); computer names are NetBIOS-like (≤ 15 letters, digits, hyphens, not all digits) | reported consistently (e.g. University of Windsor IT, "OneDrive duplicate files"; sharepointmaven.com); not in Microsoft documentation found |
| OneDrive (macOS), Dropbox | `Name (conflicted copy).ext`, `Name (<user>'s conflicted copy <date>).ext` | Dropbox help; reports for OneDrive on macOS |
| Google Drive for desktop | `[Conflict] Name.ext` (also reported as a `[Conflict]` suffix) | third-party guides (filerev.com, addictivetips.com); not in Google documentation found |
| Google Drive (web, Android) and file managers ("keep both") | `Name (1).ext`, `Name (2).ext` | widespread; the cause may also be a plain copy |
| Autosync for Google Drive / OneDrive (MetaCtrl, Android) | a "conflict" suffix with a timestamp (MetaCtrl blog, 2015); exact format not documented | low: matched by the generic `Name (… conflict …)` / `Name_conflict…` patterns |
| FolderSync (Android) | not documented (foldersync.io "Sync issues" describes when, not how) | unknown: covered only if the name contains "conflict" or "(n)" |
| Syncthing | `Name.sync-conflict-YYYYMMDD-HHMMSS-<DEVICE>.ext` | Syncthing documentation |

Because names are only a hint (and `Name (1)` is also what a plain copy gets), a file is offered for merging only when the base file `Name.notebook` exists in the same folder and both hold the **same document id**. An unrelated notebook with a similar name has its own id and is never offered. The user's sync app (Google Drive / OneDrive on Android) should be checked on the device and the table updated (testing protocol R2).

Sources: [University of Windsor IT, "Known Issue: OneDrive duplicate files"](https://uwindsor.teamdynamix.com/TDClient/1975/Portal/KB/Article/29832/Known-Issue-OneDrive-duplicate-files), [SharePoint Maven, "How OneDrive sync resolves sync conflicts"](https://sharepointmaven.com/how-onedrive-sync-resolves-sync-conflicts/), [Digital Citizen, "Cloud sync conflicts explained"](https://www.digitalcitizen.life/cloud-sync-conflicts-explained-why-files-duplicate-or-overwrite-themselves/), [FileRev, "How to find and resolve conflicted files in Google Drive"](https://filerev.com/blog/find-resolve-conflicted-google/), [MetaCtrl, "MD5 checksum in Autosync for Google Drive"](https://metactrl.com/blog/2015/07/22/drivesync-and-md5-checksum/), [FolderSync, "Sync issues"](https://foldersync.io/docs/help/syncissues), [Obsidian forum, "FolderSync conflicts on Android (through Google Drive)"](https://forum.obsidian.md/t/foldersync-conflicts-on-android-through-google-drive/37189).

## How the S Pen side button reaches a web page (0.5.1 hotfix)

Date: 2026-10-29. Trigger: with 0.5.0 on a Galaxy tablet the S Pen button did nothing, and the tablet opens Samsung's **Air command** when the button is pressed. Web search plus reading Chromium source pages; no code copied. **None of this is verified on a device**: the table separates what a source says from what is inferred.

| Question | Finding | Confidence |
|---|---|---|
| Does the Android button reach Chromium? | Chromium converts the Android `MotionEvent` button state (`BUTTON_PRIMARY`, `BUTTON_SECONDARY`, `BUTTON_STYLUS_PRIMARY`, `BUTTON_STYLUS_SECONDARY`, ...) in `ui/events/android/motion_event_android.cc`. Since Android M the stylus barrel button is `BUTTON_STYLUS_PRIMARY` (before: `BUTTON_SECONDARY`); Chromium added handling for both in 2017 (bug 721304, stylus text selection). | high that the bits are read; whether Samsung's firmware sets them is unknown |
| Mapping to `PointerEvent.button/buttons` | `ui/events/android/event_flags_android.cc` maps `BUTTON_STYLUS_PRIMARY` to the *left* mouse flag and `BUTTON_STYLUS_SECONDARY` / `BUTTON_SECONDARY` to the *right* one (read from the page; not re-checked in Blink's `PointerEvent` factory). So the S Pen button may arrive as `buttons & 1` (looking like contact), as `button 2` / `buttons & 2`, or not at all. The Pointer Events spec says barrel = `buttons & 2`, eraser = `buttons & 32` / `button 5`. | medium; the left/right split is why the test log records everything |
| `contextmenu` / long-press | A barrel press is meant to act like a right click, so a `contextmenu` (and an `auxclick` with `button 2`) is plausible. Rick Byers (Chrome) wrote on the W3C pointer-events list (2015) that the barrel button should be equivalent to the right button / context menu, and that an in-air press should be a `pointermove` plus a click rather than down/up. A touch or pen **long-press** also produces `contextmenu` on Android, so a `contextmenu` while the nib is on the page with no button signal must not be taken for the button. | medium (design intent, not observed on the S Pen) |
| Hover vs contact | Spec: a button change while hovering is a `pointermove` with `buttons` changed (no `pointerdown`); during contact it is a `pointermove` with `button` set. `pointerrawupdate` carries the same fields. | high (spec), device unknown |
| `pointerType` | Normally `pen` for the stylus tool type; some stacks might report a stylus with the button held as a mouse. The plugin accepts a `mouse` right-button event only within 700 ms of pen activity. | low |
| Samsung Air command / Air actions | The S Pen button is also a system key: Air command (floating menu on a button press while hovering), Air actions, Quick notes (button + double tap) and S Pen unlock all use it. Samsung's S Pen Remote SDK delivers button events to native apps only. A Samsung developer-forum thread (Galaxy Tab S9 FE+) reports that all pointer events arrive but the side-button press does not, in native and web code; an older thread says the button is not available to browser JavaScript. The user's tablet opens Air command on the press, so while hovering the system most likely **consumes** the button before the WebView sees it. | medium-high |
| Where to switch it off | Samsung support: *Settings > Advanced features > S Pen* has switches for Air actions, Air view, S Pen to text, Screen off memos and Quick notes; *Air command* is listed with *Menu style* and *Shortcuts*, and its on/off switch is not described on that page. The name and place differ by One UI version and model, so the plugin text says so. | path from Samsung's page; the Air command switch itself is not confirmed there |

What the plugin does with this (see `docs/architecture.md`): it accepts every plausible signal (pen `pointerdown` with `button 2` / `buttons & 2`; `buttons & 2` appearing in `pointermove` / `pointerrawupdate`, hovering or touching; a `contextmenu` from the pen but never from touch or from a bare nib long-press; `auxclick` with `button 2`; a mouse right button right after pen activity), de-duplicates them to one menu per press, keeps `buttons & 32` / `button 5` as the eraser, and adds two things that do not depend on the button reaching the app: the **Pen button test** (shows exactly what arrives) and an optional **hold the pen still** fallback. If the button turns out to arrive as `buttons & 1` (the left-flag mapping above) it cannot be told from the nib landing, and the test log is what will show it.

**0.5.2 update (user observations, Samsung tablet, 2026-10-30; not reproduced by the author).** (1) With Air command off the Pen button test received no event at all when the button was pressed: no pointer change, no `contextmenu` / `auxclick`, no key. (2) Chrome's pen-tracker page on the same tablet showed, for the pen **hovering**: `button -1`, `buttons 0`, `pressure 0`; hovering **with the side button pressed**: `button 0`, `buttons 1`, `pressure 0` (tilt present) — so the button is delivered as a *primary* press with zero pressure, not as `buttons & 2`; touching without the button: `pressure 1`, `button -1`, `buttons 1`; touching and then pressing the button: `pressure 0.92`, `button 0`, `buttons 1` (the last event only, event type unknown). `width`/`height` are 1 hovering and 0 touching in both cases, so they cannot tell the cases apart. The plugin therefore treats a pen `pointerdown` with `button 0`, `buttons 1`, `pressure === 0` after hovering as the side button, and (experimental) a dispatched pen `pointermove` with `button 0` during contact as a toggle. Both are inferred from these screenshots-of-last-event reports and are not hardware-verified.
