# Architecture — Notebook v0.4

## 1. Decision: file format

**Choice: option A — custom `.notebook` extension with versioned JSON content**, opened by a `FileView` registered with `registerExtensions(['notebook'])`.

Reasons, in order of weight for M1 (data reliability first):

1. **No one else writes to the file.** A `.md` (options B and C) is touched by Obsidian and by other plugins: Linter, Templater, automatic link updates on rename, frontmatter changes, a Markdown editor opened by mistake. Any of these can corrupt a large data block. With our own extension the file is written only by Notebook.
2. **No workspace patching.** B requires intercepting `WorkspaceLeaf.setViewState` (as Excalidraw does with monkey-around): fragile code across Obsidian versions and with the "deferred" tabs of 1.7.2+. `registerExtensions` is a public API.
3. **No indexing cost.** A `.md` with thousands of points is indexed by search and the metadata cache on every save; on Android that is a real cost.
4. **The advantages of B/C (links, tags, backlinks, Graph) belong to M4.** The format is designed to get there without rewriting the data (see §5).

Accepted and documented costs:
- Native search, tags and backlinks do not see notebooks (until M4).
- **Obsidian Sync** syncs unknown extensions only with the "Sync all other types" option enabled (stated in the README). Syncthing and USB copy have no limits.

## 2. JSON schema v6

```json
{
  "format": "obsidian-notebook",
  "version": 6,
  "id": "6f1c…",
  "createdAt": "2026-10-29T14:30:00.000Z",
  "modifiedAt": "2026-10-29T14:42:10.000Z",
  "pages": [
    {
      "id": "a91e…",
      "width": 595.28,
      "height": 841.89,
      "paper": { "kind": "grid", "spacing": 14.17 },
      "strokes": [
        { "id": "c03d…", "tool": "pen", "color": "#1e293b", "width": 2, "render": 1,
          "points": [[72.5, 90.12, 0.512], [73.1, 90.4, 0.534]] },
        { "id": "d71a…", "tool": "highlighter", "color": "#facc15", "width": 14, "render": 2,
          "points": [[72.5, 120.0, 0.5], [180.2, 120.3, 0.5]] }
      ]
    }
  ]
}
```

| Field | Rule |
|---|---|
| `format` | always `"obsidian-notebook"`: distinguishes the file from any random JSON |
| `version` | integer. A version higher than the supported one → the file opens **read-only** with a warning and is never rewritten |
| units | **typographic points (pt, 1/72 inch)**, origin at the top left of the page. A4 = 595.28 × 841.89 pt. Chosen because it is PDF's native unit (used as is by the M3a export) and independent of the screen |
| `pages` | at least one. They are stacked vertically by the layout (§6), not by coordinates. Stroke ids are unique across the whole document |
| `paper` | `kind` is one of `blank`, `ruled`, `grid`, `dotted`, `millimetre` (all but `grid` are new in v3); `spacing` in pt. See "Paper and page sizes" below |
| `points` | `[x, y, pressure]` in the page's own coordinates, x/y rounded to 0.01 pt, pressure in [0, 1] rounded to 0.001. **The saved pressure is the one actually used**: if the device does not provide it, the pressure simulated from velocity is written. Rendering is therefore deterministic. With stabilization on, the stored points are the stabilized ones (§6) |
| `tool` | `"pen"`, `"highlighter"` (new in v2) or `"shape"` (v4). The eraser produces no strokes |
| `color` | `#rrggbb` |
| `width` | nominal diameter in pt, > 0 |
| `render` | required (v5): the geometry that draws the stroke. `1` = perfect-freehand outline with the per-tool parameters below (frozen; every stroke written before v5 is 1); `2` = incremental wet-ink geometry (§6). Any other value is rejected. Written right after `width`, before `points` |
| `id` | unique strings (UUID when available) |

Added in v4 (all optional on disk, written only when present, except `meta` and `assets` which are always written):

| Where | Field | Meaning |
|---|---|---|
| document | `meta` | `{ tags, favorite, cover, bookmarks }`: library data and bookmarked page ids |
| document | `assets` | `{ [id]: { id, kind: "pdf" \| "image", path, name, bytes } }`: files in `<notebooks folder>/_assets/`, referenced by id |
| page | `background` | `{ kind: "pdf", asset, page }` or `{ kind: "image", asset }` |
| page | `elements` | text boxes (`type: "text"`: `x`, `y`, `width`, `text`, `fontSize`, `color`) and images (`type: "image"`: `asset`, `x`, `y`, `width`, `height`, `rotation`) |
| page | `infinite` | the page grows downwards while writing near the bottom |
| stroke | `tool: "shape"` | constant-width ink for lines, arrows, rectangles, ellipses and recognised shapes |

Added in v6 (optional, written only when present):

| Where | Field | Meaning |
|---|---|---|
| page | `margins` | `{ left, right, bottom }` in pt, each ≥ 0: blank space added around the background (#104). The background is drawn in the box `x = left, y = 0, width = width − left − right, height = height − bottom` (`backgroundRect` in `model/margins.ts`); without `margins` it fills the page as before. Validation: `left + right < width` and `bottom < height`, so the box keeps a positive size. Key order: after `background`, before `infinite` |

Drawing order of a page: page colour, background (PDF page or image), paper pattern (none by default on PDF and scanned pages), images, text, ink.

Unknown fields are ignored on read. Every schema change increments `version` and adds a tested migration (`src/model/migrations.ts`).

**Version history**

- **v0 → v1**: v0 is an unversioned test format (`{ strokes: [{ points: [{x, y, p}], color, size }] }`) that served to establish the mechanism.
- **v1 → v2** (M2): the only change is the new `highlighter` tool. The migration is the identity plus `version: 2`: every valid v1 document is a valid v2 document. A v1 file opened by 0.2 is migrated in memory and rewritten as v2 only on the first edit.
- **v2 → v3** (M3a): v3 adds the paper kinds `blank`, `ruled`, `dotted` and `millimetre` (the v2 reader accepted only `grid`); page sizes were already free numbers (`width`, `height`). The migration is the identity plus `version: 3`: every valid v2 document is a valid v3 document. A v2 file opened by 0.3 is migrated in memory and rewritten as v3 only on the first edit.
- **v3 → v4** (M3): adds `meta` (`tags`, `favorite`, `cover`, `bookmarks`) and `assets` (keyed by lowercase-hex id) to the document; `background`, `elements` (text and image) and `infinite` to pages, written only when present; and the stroke tool `shape`. Migration: default meta (`DEFAULT_META`), empty assets; a pre-v4 file that already contains `shape` is rejected. Validation: asset references (page backgrounds, image elements) must resolve to an asset of the right kind; ids are unique across strokes and elements; `meta.tags` are de-duplicated and `meta.bookmarks` filtered to existing pages on read and on write. Order of keys: `meta`, `assets` before `pages`; per page `background`, `infinite`, `elements`, `strokes`. `serializeChecked` validates meta, assets, backgrounds and elements on every save, also on the incremental path.
- **v4 → v5**: adds the required per-stroke `render` field (`1` = `RENDER_FREEHAND`, `2` = `RENDER_INK`). Migration: every stroke of every page gets `render: 1`, because every stroke written before v5 was drawn with perfect-freehand and must keep rendering exactly as before; v0→v1 still produces strokes without `render` and the v4→v5 step adds it. `readStroke` rejects a missing `render` or a value other than 1 or 2 (`pages[i].strokes[j].render`). `createStroke` defaults to `RENDER_FREEHAND`, so only a caller that asks for the new engine produces render 2. Key order: `id`, `tool`, `color`, `width`, `render`, `points`.
- **v5 → v6** (PDF wave p1a): adds the optional page field `margins`. Migration: the identity plus `version: 6`; a `margins` key already present in a v5 file is dropped, because a v5 reader ignored it (it was never ours and never had an effect). No other field changes, so every valid v5 document is a valid v6 document without margins. A 0.4.x plugin opens a v6 file read-only (future version) with a backup and never rewrites it, so margins cannot be lost by an older version saving over them.
- **Compatibility**: a plugin that supports an older version sees a newer `version` as a future version, so it opens the file read-only (and keeps a backup copy of it, as for any file it cannot edit) and never rewrites it. Once 0.2 has saved a file, 0.1.x cannot edit it; once 0.3 has saved a file, 0.2.x cannot edit it; once 0.4.0 has saved a file (v5), 0.3.x and earlier open it read-only.

**Stroke rendering parameters** of `render: 1` (perfect-freehand) are code constants; the per-stroke `render` field selects the geometry, it does not carry parameters:
- pen (`PEN_V1`): `size = width`, `thinning 0.6`, `smoothing 0.5`, `streamline 0.35`, `simulatePressure false`, round caps. Unchanged since v1;
- highlighter (`HIGHLIGHTER_V2`): `thinning 0` (constant width, pressure ignored), `smoothing 0.5`, `streamline 0.35`, flat ends. Painted with alpha 0.35 and `multiply` compositing.

Changing these constants changes how existing files look: the `render: 1` parameters are frozen. A different look is a new `render` value (2 = wet ink, §6), never an edit of these constants.

### Paper and page sizes

Both are per page, so one notebook can mix them. Constants are in `model/types.ts` (sizes, default spacing) and `ink/paper.ts` (pattern geometry).

| Paper `kind` | Default `spacing` | Pattern |
|---|---|---|
| `blank` | unused | nothing drawn |
| `ruled` | 8 mm | horizontal lines every `spacing`, the first at 3 × `spacing` from the top (`RULED_TOP_LINES`); a red vertical margin line at 25 mm from the left edge |
| `grid` | 5 mm (14.17 pt) | vertical and horizontal lines every `spacing` |
| `dotted` | 5 mm | a dot at every grid intersection |
| `millimetre` | 1 mm | lines every `spacing`; every 10th (10 mm) is a major line, drawn darker |

Lines and dots are never drawn on the page edge. `paperPattern(page, visible, { includeMinor })` is pure (no canvas): it returns lines (`minor` / `major` / `margin`) and dots in page coordinates, limited to the visible rectangle. The canvas renderer (`drawPaper`) and both exporters use it, with shared colours (`PAPER_COLORS`), so screen and export show the same pattern. On screen, minor lines and dots are left out when they would be closer than about 3 CSS px (`minorVisible`), which keeps millimetre paper cheap and readable when zoomed out; major and margin lines stay. Exports always draw the full pattern.

Page size presets (portrait, pt): A4 595.28 × 841.89, A5 419.53 × 595.28, Letter 612 × 792. Landscape swaps width and height; there is no stored orientation field, it follows from `width > height`. The format accepts any positive `width` and `height`; the UI offers only the presets, plus the size of imported PDF pages and of scanned or image pages (custom sizes are not implemented).

**Changing the size of a page does not move or scale its strokes.** They keep their page coordinates; strokes that end up outside a smaller page stay in the file (nothing is deleted) and are clipped when drawn and exported. Making the page large again shows them again.

A page added with **Add page** copies the size and paper of the page in view (0.2 always added an A4 grid page); `createPage()` without arguments still gives A4 grid.

## 4. Save flow (rule 4: zero data loss)

Session state: `doc`, `revision` (incremented on every change), `savedRevision`, `diskContent` (last content read or written by us), `mode` = `ok` | `readonly` (future version) | `broken` (unreadable) | `deleted`. **All disk operations of a session (load, flush, external-change check) run one at a time through a single queue**, so a check never interleaves with a write.

**Open**
1. `vault.read(file)` → `parse()`.
2. Success → `mode = ok`, any migration happens in memory (the migrated file is rewritten only on the first change).
3. Failure (invalid JSON, invalid schema, empty file) → `mode = broken`; future version → `mode = readonly`. In both cases: **a backup of the raw content is created** in `<notebooks folder>/_backup/<name> <date-time> <reason> <hash>.bak` (no duplicates: a backup is skipped only if a file with the same hash in its name has exactly the same content), the view shows a message and **no write path is active**.

**Change** → `revision++` → scheduled save: 1.5 s debounce from the last change, at most 10 s of waiting during continuous writing.

**Flush** (debounce, view close `onUnloadFile`/`onClose`, plugin `onunload`, `visibilitychange` → hidden, `pagehide`, `workspace 'quit'` best effort):
1. If `mode ≠ ok` or there are no changes → nothing.
2. `serializeChecked(doc)` produces `next` and **re-validates** it (see "Save check" below). If it fails: no write, warning, changes kept in memory.
3. `current = vault.read(file)`; if `current ≠ diskContent` the file changed outside of us (Sync, another device) → `current` is saved as a `conflict` backup **before** anything is overwritten, and the user is notified. If the backup fails, the write does not happen.
4. `vault.process(file, latest => …)` (atomic): if `latest ≠ current` the file changed again since step 3 → it is returned unchanged (nothing overwritten) and steps 3–4 are repeated, at most 3 times; then the save fails and is retried later.
5. `diskContent = next`, `savedRevision = revision` captured at step 2. Changes arriving during a flush schedule another one. A failed write keeps the changes in memory and retries after 5 s.

**Save check** (`serializeChecked`). Committed strokes are frozen (`freezeStroke`: immutable; an edit creates a new stroke), so their serialized line can be cached safely. A **new** stroke (drawn in this session) is serialized, parsed and validated, re-serialized, and the text must be identical; the verified line is cached per stroke object, so each stroke goes through this once. A stroke **read from a file** was already validated field by field by `parse()` and is marked as such (a `WeakSet`), so on the first save it is only serialized, without a second parse. After a successful load the session warms the line cache one page per timer tick (`DocumentSession.warmUp` → `warmStrokeLines`), so that first save is cheap. Duplicate stroke ids are rejected. Then:
- documents whose text is under `FULL_CHECK_LIMIT` (1 MB) are **fully re-parsed** on every save and must satisfy `serialize(parse(next)) === next`, as in 0.1;
- larger documents get the **incremental check**: the skeleton (header, pages, paper, page ids) is parsed and validated on every save, plus the strokes not seen before, plus the duplicate-id check. The full re-parse is skipped, so saving a notebook of several MB no longer re-parses all of it each time.

The text is still assembled in full on every save, so the cost of a save stays proportional to the document; only the parse and validation work is avoided. Opening a file always does a full `parse()`.

**Closing a view or switching file** (`onClose`/`onUnloadFile`): the stroke in progress is committed, then the flush is attempted up to 3 times; if the changes still cannot be written they are saved as an `unsaved` backup before the session is released.

**Deleted file**: the session stops writing (`mode = deleted`); unsaved changes, if any, go to an `unsaved` backup.

**External modification** (`vault.on('modify')` on the open file): the check is queued after any flush in progress and re-reads the file; if the content matches `diskContent` it is the echo of our own write → ignored. Otherwise, with no pending local changes → reload the document (if unreadable → `broken` + backup, without overwriting); with pending changes → ours are kept and on flush the external content ends up in the `conflict` backup.

**Stroke in progress**: on `visibilitychange`/`pagehide`/`pointercancel` the stroke in progress is closed and saved as a normal stroke before the flush, so leaving the app mid-writing does not lose it.

Known limit: if Android kills the process without notifying `visibilitychange`, at most the last ~1.5 s of changes are lost (or 10 s during continuous writing). Closing from recent apps first goes through the "background" state, so the flush happens; this needs to be verified on hardware.

**Instant save journal** (`src/storage/journal.ts`, M8 #31). 200 ms after a change (never during a gesture) the session records the document in `<config dir>/plugins/<plugin id>/journal/<doc id>.<0|1>.journal`, through `app.vault.adapter` (plugin-owned technical file: no vault events, no sync, no indexing). The entry is the serialized text itself: whole for notebooks under 256 KB, otherwise a line diff against `diskContent` (one stroke per line, so adding a stroke journals a few hundred bytes); a huge diff falls back to a full snapshot throttled by size, and nothing is journaled above 8 MB. Two slot files are written alternately, so a torn write leaves the previous entry intact; entries carry fingerprints of the base and of the resulting text. On open, an entry whose base is the file just read is applied in memory and the session is dirty, so the normal save writes it; the journal is deleted only after that save (and after every successful flush that leaves no newer changes). An entry already contained in the file is just deleted. An entry whose base differs (the file changed elsewhere) or that cannot be rebuilt is **never applied**: a copy goes to the backup folder (`journal` reason) before the journal is deleted, and if that copy fails the journal is left untouched. Journal I/O has its own queue; its failures are reported once and never affect saving. A notebook that cannot be parsed has no journal lookup (its document id is unknown). Entries are keyed by document id **and** file path (`journalKey`), so a copied file with the same id, or two sessions, cannot replay each other's entries; when a notebook goes from unreadable to readable (`broken` → `ok`) the journal lookup is done again.

**Format layer** (`storage/format.ts`). The only module that knows what a notebook file is (`NOTEBOOK_EXTENSIONS`, `isNotebookFile`) and how the document text is taken from and put back into the raw file text (`readNotebookText`, `writeNotebookText`). The session, library, index, embeds, history, scanner and PDF import use these helpers instead of testing `.notebook` or reading raw text, so a later container change (M4: Markdown, §5) is confined here. The version snapshots and the journal store the document text as `readNotebookText` returns it.

**Version history** (`storage/history.ts`, `integration/history-service.ts`). On `file-open` and `modify` of a notebook, a snapshot is written (the file is read at once, so the snapshot is the content as it was on open, but it is parsed and written only after `whenIdle`, so a second full parse does not compete with the first paint; see Instant start) if the newest one is older than `snapshotIntervalHours` (default 24; 0 = off): `<notebooks folder>/_backup/history/<document id>/<YYYYMMDD-HHmm>.snapshot`, the document text byte for byte. Beyond `snapshotsToKeep` (default 10) the oldest go to the Obsidian trash. The command **Restore a previous version** lists the snapshots (date, page count, size), asks for confirmation, then: flushes the open notebook (restore stops if that save fails), checks that the snapshot's document id matches the file (a snapshot of another notebook is refused; if the file is unreadable it asks again), saves the current content as a `before-restore` backup, and writes the snapshot through the same checked path as a normal save. Open views reload the result.

**Instant start** (`view/last-location.ts`, `storage/idle.ts`, #271). The page being read goes into the workspace layout through `getState()` (`{ file, page }`, the same `page` that links use, applied by `setState`), saved by `requestSaveLayout` a second after it changes; the plugin also keeps the last notebook path and page in its settings for the command *Continue last notebook*. Neither is part of the notebook file. Work nobody is looking at is kept out of the first paint: the version-history snapshot parses after `whenIdle`, the stroke-line warm-up of the save check starts `WARM_UP_DELAY_MS` (400 ms) after the load, the page panel and thumbnails only work when open, PDF pages and images load on demand. Nothing in the load path was weakened: the document is still parsed, migrated and validated in full before it is shown, and a save before the warm-up has finished computes the lines it needs itself. Measure with `npm run bench:open` (headless Chrome, in-memory vault: CPU time only; not Android).

**Input routing** (`ink/input-policy.ts`, `ink/edge-zones.ts`, `ink/radial.ts`, `view/radial-menu.ts`, #151, #152). Routing is policy around the pointer controller; the stroke pipeline (sampling, wet ink, geometry, stabilizer) is untouched. A touch that starts in an enabled edge zone (`edgeRejection`, `edgeRejectionPx`, one switch per edge) routes to `ignore`. The pen side button (`button 2` or `buttons & 2`) follows `penButtonAction`: `radial` routes the pen-down to `menu` (no stroke, and the pen is not marked down for palm rejection because no stroke will end it; a press while hovering is detected on `pointermove` once per press), `eraser` draws as the eraser while held, `off` keeps the previous behaviour (a contact with the button held draws, a bare button press is ignored). The eraser end and the eraser button (`button 5`, `buttons & 32`) always erase. **0.5.1:** the detection is in `ink/pen-button.ts` (`BarrelDetector`, pure). Pen events (`pointerdown` with `button 2` / `buttons & 2`, `buttons & 2` appearing in `pointermove` / `pointerrawupdate`), a pen `contextmenu`, a pen `auxclick` (button 2) and a mouse right button within 700 ms of pen activity each start at most one menu per press; touch never does, and a pen `contextmenu` while the nib is on the page without a recent barrel signal (a long-press) is ignored. The eraser bits are never the side button. While a pen stroke is in progress the menu opens only if the stroke is younger than 350 ms and has not left a 6 px radius (the stroke is discarded, no dot); otherwise the press is ignored. The optional still-hold fallback (`penLongPress`, off by default) discards the stroke and opens the menu after 600 ms within 6 px. The *Pen button test* modal (`view/pen-test-modal.ts`, log logic in `ink/pen-button.ts`) shows the raw events. While the radial menu is open it listens on `window` in the capture phase and stops the pointer events, so nothing reaches the page; the ring is placed by `clampCenter`, sectors are hit-tested by `sectorAt` (sector 0 at the top, clockwise), and a sector is chosen by lifting or tapping on it or by releasing the button over it.

**Repair of a damaged notebook** (#140; `model/lenient-json.ts`, `model/repair.ts`, `storage/recovery.ts`, `integration/reliability.ts`). A `broken` view shows a **Repair…** button (also the command *Repair damaged notebook*). Nothing is written to the damaged file; it already has its `unreadable` backup. The repair reads the text in four steps: (1) `parseLenient` reads the JSON up to the first damage, closing the open objects and arrays there; a value read only in part (a cut number or string) is dropped, never guessed; (2) if the JSON was not complete, a line scan reads the layout `serialize()` writes (one stroke, element and asset per line, page fields on their own lines), so strokes after a damaged region in the middle are recovered too, matched by id (a stroke cut off in step 1 is replaced by its intact line); (3) the result goes through the regular migrations, and if the whole document does not migrate, pages and then single strokes are migrated one at a time; (4) every page, stroke, element, asset and the metadata are checked by the regular `validate()` on a one-item document, so the rules live in one place and a later format version is handled by its own migration and validator. Items that fail get conservative fixes (invalid points dropped, pressure clamped, unknown tool → pen, invalid colour → black, missing render → 1, duplicate id with different content → new id, exact duplicates kept once; page size and paper fall back to A4 grid, an unusable background is dropped and the page kept) and are kept only if they then validate; everything else is counted as lost. Unknown fields (e.g. from a newer version) cannot be carried over, because the model and the serializer only know the current fields: they are counted and stay in the original. Further sources: version-history snapshots, backup copies of the same file name whose document id matches, and journal entries of the file (full entries as they are; delta entries only on top of a text whose fingerprint is their base). Each source is repaired the same way and ranked by recovered items (strokes + elements + pages), then by date; the dialog shows every source with its summary, preselects the first and also offers *the damaged file and the best other source together* (merged with the rules below). The result is written with a **new document id** into a new notebook `<name> (repaired)` next to the original (so journal, version history and the library keep the two apart), read back and opened. A newer-version file is not repaired (it opens read-only).

**Conflicted copies** (#122; `storage/conflicts.ts`, `model/merge.ts`, `integration/reliability.ts`). A file in the same folder is treated as a conflicted copy of `Name.notebook` only if its name matches a sync-client pattern (`Name (1)`, `[Conflict] Name`, `Name [Conflict]`, `Name-<DEVICE>[-n]` from OneDrive, `Name (… conflict …)`, `Name_conflict…`, `Name.sync-conflict-…`; sources in `docs/research.md`) **and** it holds the same document id (a copy made by sync keeps the id; an unrelated notebook does not). When a notebook loads, or such a file is created while it is open, a notice offers **Merge…** (also the command *Merge conflicted copies*). The dialog shows, per copy, what would be added (`planMerge` summary). Merge rules: union of pages, strokes, elements and assets by id; the same id with different content keeps the main version and adds the copy's as a copy with a new id, unless that page already holds identical content (which makes a second merge a no-op); nothing is ever removed (deletions are not inferred); page settings (margins included) and the cover of the main notebook are kept (differences are counted); when a common page has a different left margin in the copy, the copy's strokes and elements are first moved by the difference of the left margins into the main page's frame, so ink identical relative to the background is recognised as identical and new ink lands where it was drawn on the background (`mergeCovers` compares in the same frame); when new ink of the copy would then fall off the main page (left of it because the copy has the wider left margin, or beyond its right or bottom edge, also with equal margins; text boxes count with their wrapped height), the main page grows just enough in the same Batch, counted as `pagesEnlarged`: wider margins through `SetPageMargins` on a page with a background (its own ink moves with the background), more height through `SetPageSize` (margin rule `marginsAfterResize`) on an infinite page, a larger size on a plain page; tags and bookmarks are united, favourite is "either". Pages only in the copy are inserted after the page that precedes them in the copy. Properties covered by tests: nothing of either side is lost (`mergeCovers`), idempotent, commutative for the content of each page, and one undo step that restores the exact previous file. The copy stays where it is; optionally it is moved (never deleted) to `_backup/conflicts/`, only after `flushNow()` succeeded and the file read back from disk contains everything of the copy. A copy that cannot be read is offered for repair instead.

**Restore one page** (#180; `model/page-restore.ts`, `integration/reliability.ts`). Page menu → *Restore page from a previous version…* (or the command): pick a version-history snapshot or a backup copy of this notebook (same document id), see its pages as thumbnails (the page with the same id, else the same position, is preselected), then *Replace current page* (`ReplacePage`: same page id, so bookmarks and links still work; content ids are kept unless another page uses them) or *Insert as new page* (`duplicatePage`, new ids). Assets the old page needs and the notebook no longer lists are added back (`AddAsset`). One `Batch`, one undo step; the rest of the notebook is untouched. The journal is not a source here: for a notebook that opens normally its entries are either already applied at open or belong to the live session.

## 5. Format evolution (toward M4)

- The container is isolated in `storage/format.ts` (§4), so the options below change that module and the migration, not the library, journal, history or embeds.
- **C (hybrid)**: implemented as O1 (companion notes, §12): a `.md` per notebook with properties and the text of its text boxes; the JSON does not change. Its content generator does not depend on the container, so it also serves B.
- **B (`.md` with data block)**: if B is chosen, the migration will be a file → file conversion: the JSON becomes the content of a code block, with `format`/`version` unchanged. The parser stays the same.
- Many strokes: v2 keeps a single JSON file (a generated 10,000-stroke notebook is about 6.8 MB on the PC). If that proves too slow on the device, a later version may split pages across files; `version` enables the migration. Decide with benchmark numbers from real hardware.

## 6. Input, rendering and tools

### Input
- `touch-action: none` on the container; `pointerType` distinguishes `pen`/`touch`/`mouse`.
- **Palm rejection.** Time-based: if the pen is active or was seen (even hovering) in the last N ms (default 500, configurable), touch does not draw and only pans (one finger) or zooms (two fingers). "Write with finger" mode is a setting (default off). If the pen touches down while a finger is drawing, the finger stroke is discarded. Contact size (experimental, default off): a touch whose `max(width, height)` exceeds the setting (CSS px) is ignored completely, scrolling included; it depends on what the device reports.
- **Samples.** With *Low-latency ink* on, the drawing pointer is read from `pointerrawupdate` where the WebView has it (Chromium in a secure context: samples are dispatched as the OS delivers them, not once per frame) and from `pointermove` otherwise, always with `getCoalescedEvents()`. Both events report the same samples, so each sample is delivered once: a sample is new only if its timestamp is later than the last delivered one (or equal with a different position; once `pointerrawupdate` has delivered samples in a stroke, `pointermove` only adds strictly later ones, so a batch sharing one timestamp is not repeated). Samples go into preallocated typed arrays (`SampleBuffer`: x, y, pressure, time), converted to page coordinates inline: no object per sample on the writing path. Navigation (pan, pinch) stays on `pointermove`.
- **Prediction** (`getPredictedEvents()`): setting *Predicted ink*, **default off**. Predicted samples are only drawn at the tip of the wet ink and erased at the next sample; they are never stored. Off by default because they overshoot at sharp turns and at the end of a stroke (the tip "jumps" ahead and back), which is one of the reported problems; the gain cannot be measured without the device. The setting key changed (`prediction` → `inkPrediction`), so the new default applies to everyone.
- **Pressure** is decided **once, when the stroke starts**, and never switches in the middle of it (the previous model trusted real pressure after three distinct values, which changed the width inside the first stroke). Real pressure is used if the device already proved it (≥ 3 distinct values in (0, 1), 0.5 excluded, in earlier strokes) or if the stroke's first sample is already in (0, 1) and not 0.5; otherwise the stroke uses pressure simulated from speed, and a device that proves real pressure meanwhile uses it from the next stroke. A trusted pen that then reports one value for 200 samples in a row loses the trust for later strokes. Real pressure gets a light causal smoothing (factor 0.6 per sample). "Always simulate pressure" setting.
- **Stabilization** (setting 0–10, default 2): an adaptive low-pass, the 1€ filter (`one-euro.ts`, after Casiez, Roussel and Vogel, CHI 2012; own implementation), on screen coordinates before conversion. Its cutoff rises with speed: when the pen is nearly still it removes tremor and digitizer jitter, when it moves the lag drops towards zero. Level L maps to `minCutoff = 20/L Hz`, `beta = 0.2/L Hz per px/s`, `dCutoff = 4 Hz`; 0 turns it off. On synthetic 240 Hz input, level 2 leaves 35% of the jitter at rest (the old exponential stabilizer at level 2: 53%) and lags 1.2–1.5 px at 300–1000 px/s (old: 1.5–5 px); level 10 leaves 15% (old: 27%) and lags 6–7 px (old: 7.5–25 px). The filtered point is what gets stored; the drawn tip follows the raw pen position, and when the pen lifts the raw position is added as the last point, so the line always ends where the pen did.
- Samples closer than 0.5 CSS px to the last stored point are not stored (the tip still follows the pen).
- **Fling**: when a one-finger pan ends with `pointerup`, the speed over the last 80 ms continues as an inertial scroll with exponential decay (time constant 325 ms); a new touch or wheel event stops it. Two-finger pan/zoom has no inertia.

### Pages: layout and virtualization
- `layoutPages` stacks the pages vertically in "document space" (pt) with a 24 pt gap, each page centred horizontally on the widest one. Strokes stay in page coordinates; a page box is only an offset, so layout changes never touch stroke data.
- The viewport maps document space to the screen. Fit-to-width uses the layout width; zoom is clamped to 0.25–8.
- **Virtualization**: the static redraw asks `visiblePages` for the pages intersecting the screen and draws only those; within a page it skips strokes whose cached bounding box is outside the visible area. Stroke `Path2D`s and bounds are cached per (frozen) stroke object and built the first time a stroke is drawn.
- **Add page** (toolbar button and command) inserts a blank page with the size and paper of the page in view **after the page at the centre of the view** as an undoable `AddPage`, then scrolls to it. The toolbar shows `n / total` for the page at the centre of the view. Further page commands are in "Page commands" below.

### Page commands

The toolbar's "more" menu has *Add page* and *Page options* (the page menu). It acts on the page at the centre of the view. Every item is a history command, so each is one undo step; the selection is cleared first, and nothing runs while a stroke is being drawn.

| Menu item | Command |
|---|---|
| Duplicate page | `AddPage` with `duplicatePage(page)` after the current page: new page id, new stroke ids, copied points, same size and paper |
| Move page up / down | `MovePage`; disabled at the first / last page |
| Delete page | `DeletePage`; disabled when the notebook has one page (a document always keeps at least one). Undo re-inserts the same page object |
| Paper: blank / ruled / grid / dotted / millimetre | `SetPaper`; the spacing becomes the default of the new kind |
| Size: A4 / A5 / Letter | `SetPageSize`; keeps the current orientation; strokes are not moved or scaled |
| Portrait / Landscape | `SetPageSize` swapping width and height; shown only when the page has a preset size |
| Export page as PDF / notebook as PDF / page as SVG | see §8 (not history commands) |
| Page margins… (pages with a background) | `SetPageMargins`, or a `Batch` of them with *All pages of this PDF* (§10) |
| Update PDF from a new version… (PDF pages) | one `Batch` from `planRepublish` (§10) |
| Export PDF annotations to Markdown (PDF pages) | not a history command (§10) |

After a command the view scrolls to the affected page. The commands tolerate repeated apply/revert: no page is inserted twice and a refused delete is not "undone".

### Rendering
- Canvases stacked in the view, sized to it × `devicePixelRatio`: **static** (paper pattern, saved strokes of the visible pages; a new stroke is appended without redrawing everything), **live** (lasso, floating selection, ruler, shape-tool preview and recognised shapes; redrawn with `requestAnimationFrame`) and **wet** (the pen or highlighter stroke being written, see "Writing engine"). Only the pen's wet canvas can ask for `desynchronized: true` (low latency: Chromium may present it without waiting for the compositor), and only with the *Low-latency ink (experimental)* setting (default off since 0.4.1: on some Android GPUs a desynchronized canvas can be promoted to an overlay composited as opaque); if the low-latency context cannot be created, a regular one is used, and `getContextAttributes().desynchronized` tells what was granted. A second, regular wet canvas is created on first use for the highlighter.
- **Guards** (0.4.1). Each step of a frame (static layer, live layer, wet-canvas release) and each part of a page (background, paper, every element and every stroke) and of the live layer (selection, ruler, lasso, preview) runs in its own try/catch: an exception skips that part, is logged once per kind as `[notebook] render <part>` and leaves the context reset before the next full redraw, so one bad stroke, image or PDF page cannot blank the page. If painting wet ink throws, wet ink is turned off for the view and strokes being written are shown on the live layer at the next frame (the pre-0.4 path), so the pen always leaves ink. The pointer controller guards each event the same way (`[notebook] input <event>`) and always closes the stroke on pointer-up.
- **Highlighter** strokes are filled with alpha 0.35 and `globalCompositeOperation = "multiply"` in stroke order, so they darken what is under them (paper, grid, earlier ink) instead of covering it. While writing, the highlighter's wet canvas holds the stroke opaque and CSS gives the canvas `opacity: 0.35; mix-blend-mode: multiply`: the same result over the page as the committed stroke, and overlapping parts of the stroke never darken twice.
- **CSS-transform fast path**: pan and zoom gestures call `setViewport(v, interactive = true)`. If the last full static redraw took more than 12 ms, the existing bitmap is moved and scaled with a CSS `matrix(...)` transform instead of being redrawn, and a full redraw runs 120 ms after the last gesture update. Any non-interactive change redraws immediately. While only the transform is applied, areas the old bitmap did not cover are blank and detail is not re-rendered for the new zoom. Pages that redraw in 12 ms or less never use it.
- Initial zoom: fit to the view width; recomputed on resize/rotation until the user zooms. Pinch, wheel and Ctrl+wheel zoom around the focal point.
- **Performance overlay** (setting): frame interval and input→frame (time from the last input sample to the next drawn frame), and for the wet ink input→paint (event timestamp to the end of the handler that painted it) and the processing time per input event, whether `pointerrawupdate` is in use ("raw"), the last static redraw time and the strokes and pages drawn; refreshed twice a second. These are software measures, not display latency.

### Writing engine

What was wrong (measured or confirmed in the code, PC numbers; see "Benchmarks"):
1. The live stroke was rebuilt **whole** every frame: perfect-freehand outline of all points (`last: false`), SVG string, `new Path2D(string)`, full-canvas clear and fill. On the PC a 1.5 s stroke at 240 Hz cost 11.4 ms of outline building in total (90 rebuilds, growing with the stroke) against 0.03 ms for the new geometry, and a lot of garbage per frame (a 7,200-sample replay in Node: 56 minor collections, the new path 1).
2. Visible **jumps**: perfect-freehand does not draw the start of a stroke until the pen has moved one stroke width, rounds the end differently with `last: false` than with `last: true`, and the predicted points (on by default) were part of the same outline, so the tip overshot and pulled back; at pen-up the committed outline (`last: true`, stabilizer catch-up points) replaced the live one; in the first stroke of a session the pressure switched from simulated to real in the middle of the line.
3. **Main-thread work during writing**: the debounced save (1.5 s after a stroke) and the 10 s max-wait save did not check for a gesture in progress, so a full `serializeChecked` (30 ms on the PC for 10,000 strokes) could run in the middle of the next stroke; the journal (200 ms after a stroke) waited only while the pen was down, so it typically serialized in the short gap between two strokes and delayed the first samples of the next one.
4. Frame-aligned input: `pointermove` is dispatched once per frame, so a sample waited on average half a frame before anything was drawn.

The new pipeline:
- **Geometry** (`ink-geometry.ts`, render version 2): the stored points are joined by a centripetal Catmull–Rom curve (no cusps or loops between uneven samples), subdivided into pieces of at most 1.5 pt (≤ 16 per segment). Along it sit *nodes*: discs whose radius follows the pressure with PEN_V1's response (`width × (0.2 + 0.6 p)`; highlighter: constant `width / 2`). The stroke is the union of the discs and the tangent trapezoids between consecutive discs. The curve between points k and k+1 depends only on points k−1…k+2, so its nodes are **final** as soon as point k+2 exists (or the pen lifts): the geometry is causal and incremental, and the nodes built while writing are exactly the nodes built later from the saved points (a test checks equality at every step).
- **Wet ink** (`wet-ink.ts`): each input event filters and stores its samples, then paints at once, in the handler (no animation frame): (1) the capsules (disc + trapezoid) that just became final, once; (2) the previous provisional tip is erased by clearing its dirty rectangle and repainting, clipped to it, only the final capsules whose boxes meet it (found through the bounding boxes of chunks of 64 capsules, so long strokes do not slow it down); (3) the new tip: straight capsules from the last final node through the stored points not final yet, the raw pen position and, if enabled, the predicted samples. Nothing is redrawn whole: the work per event stays constant as the stroke grows (a test counts the canvas calls and the capsules looked at over 2,000 samples). Each event fills its own capsules, so where two events' capsules meet, antialiased edge pixels are composited twice: a sub-pixel difference from the single fill of the committed path. The first point shows as a dot immediately.
- **Commit** at pen-up: the raw end point is added, the last segment becomes final and is painted, and the frozen stroke (render 2) is drawn on the static layer with the committed path of the same nodes; then the wet canvas is cleared. The committed path is the same area with far fewer edges: the node chain is cut into runs where it bends gently (< 25° between consecutive trapezoids, no side stepping backwards), each run is one polygon through the tangent points, and a disc is kept at each end of a run; inside a run it differs from the union of capsules by at most 2.4% of the radius on the outer side of bends (a test fills both on a fine grid: under 0.4% of the area differs). The pen's wet canvas is cleared one frame after the static layer shows the stroke, because a desynchronized canvas may be presented before the compositor frame (meanwhile the same opaque ink is simply shown twice); the highlighter's regular canvas is cleared at once. Copying the wet pixels to the static layer was tried and dropped: reading back a desynchronized canvas cost 2–4 ms on the PC. The static layer is never redrawn whole for a single stroke (except when an infinite page grows, as before).
- **Recognised shapes** (hold still 0.6 s) leave the wet layer: the shape is drawn on the live layer with perfect-freehand like before and committed as render 1; the shape tool is unchanged.
- **Main thread while writing**: the session's timed work (debounced save, max-wait save, journal entry) waits while a gesture is in progress and for 350 ms after it ends (`quietMs`), but never more than 4 s after it was due (8 s while the pen stays down or a text box is open); a deferred save keeps its due time (new strokes do not push it back), and the save and the journal have separate clocks, so continuous writing cannot hold saving back; explicit flushes (closing, `flushNow`) never wait. Page-panel thumbnails are not refreshed while writing.
- **Render versions**: every stroke records its geometry (`render`, format v5). Strokes written before v5 are render 1 and keep perfect-freehand with the frozen PEN_V1/HIGHLIGHTER_V2/SHAPE_V4 parameters, so existing notebooks look exactly as before; the renderer, SVG and PDF export pick the geometry per stroke (PDF writes discs as four cubic Béziers, SVG as two arcs, both nonzero fills). Library thumbnails (`library/thumbnail.ts`) use the same render-aware path (`strokeSvgPath`).

### Tools
- **Whole-stroke eraser**: 10 screen px radius converted to pt; the segment travelled by the eraser between two events is tested against the stroke's segments (with half the stroke width), with a bounding-box prefilter.
- **Segment eraser** (`eraseSegment`): same hit test, then the stroke is densified (no segment longer than half the radius, so a cut cannot slip between two distant points) and the points within `radius + width/2` of the eraser path are removed. Surviving runs of at least two points become new strokes with new ids and the original style; single-point crumbs are dropped. The original is replaced in place by a `ReplaceStroke`. The eraser acts on the page under the pointer, so one gesture can cross pages.
- **Gesture undo**: everything erased in one gesture (either mode, any number of pages) is recorded as a single `Batch`, so one undo restores it.
- **Lasso** (`lasso.ts`): the gesture polygon is tested with an even-odd rule; a stroke is selected when at least 50% of its points are inside. A selection belongs to one page. It shows a dashed frame, a **resize handle** at the bottom-right corner (uniform scale about the top-left corner of the frame, clamped to 0.05–20×) and a **rotate handle** above the top edge (rotation about the centre of the frame). Dragging inside the frame moves it.
- **Selection actions** (`view/selection-actions.ts`, no format change): a bar outside the stage (so its taps never reach the pen input) over the selected items. *Restyle* builds one `Batch` of `ReplaceStroke`/`ReplaceElement` (`ink/restyle.ts`); a request names a group (ink or highlighter) and never touches the other. *Copy* deep-copies strokes and elements into a module-level clip (`view/clipboard.ts`, shared by every notebook view of the session) and reads the image bytes; it also writes a marker text (`[Notebook selection: …]`) to the system clipboard so a later paste can tell whether something newer was copied elsewhere (`decidePaste`). *Paste* stores the images again through `storeAsset` when the target document lacks them (content-addressed, so a shared `_assets/` stores nothing twice), instantiates the clip with new ids at the centre of the view and adds it as one `Batch` (`AddAsset`, `AddStroke`, `AddElement`); *Duplicate* does the same inside the notebook without touching the clipboard. Pasting a system-clipboard picture or text goes through `navigator.clipboard` or the paste event, with a paste box where the WebView cannot read the clipboard. *Make white transparent* decodes the image (at most 2048 px), clears near-white pixels (`ink/image-alpha.ts`), stores a PNG as a new asset and replaces the element (`AddAsset` + `ReplaceElement`); no field is added to the file.
- **Objects wave 0.6** (no format change). *Ink attached to objects* (`ink/attach.ts`, `view/object-ink.ts`): a stroke belongs to the topmost element (image rotated box, laid-out text box) that holds at least `ATTACH_SHARE` (60%) of its points; there is no stored link, so the answer is recomputed from the geometry. `commitSelectionTransform` adds a `ReplaceStroke` for every such stroke that is not selected itself to the same `Batch` as the selection, and the live overlay draws them with the dragged matrix (the answer is cached while the selection is unchanged). Deleting elements computes the ink on them before the `Batch` runs and offers a second, separate undo step (`deleteInkCommand`) in a notice; the button does nothing if the elements are back. Setting `inkFollowsObjects` (default on) turns both off. *Personal stamps* (`ink/stamps.ts`, `storage/stamps.ts`, `view/stamp-palette.ts`): a stamp is a `.stamp` file in `<notebooks folder>/_stamps/` that contains a notebook document with one page (moved to the origin), so parsing, validation, asset records and future migrations are the notebook's own; `serializeStamp` re-validates the text before anything is written and `saveStamp` reads the file back. Placement (`planStampPlacement`) is `instantiateClip` + `pasteCommand`: new ids, one `Batch` that also registers the assets the document lacks; images whose file cannot be found are left out with a notice. Built-in stamps are shape-tool strokes generated in code with the current pen colour and width.
- **Transforms** are kept as an affine matrix (`transform.ts`) while the pointer is down: the selected strokes are hidden from the static layer and drawn on the live layer with the matrix, so a drag redraws only the selection. On release the matrix is baked into new strokes (`transformStroke`: points transformed and re-quantized, width scaled by the matrix's uniform factor, same id and style) and applied as a `Batch` of `ReplaceStroke` commands: one undo step. Delete (toolbar button, Delete or Backspace) is a `Batch` of `ReplaceStroke` with no replacement. Escape or changing tool clears the selection. Transformed strokes stay on their page and are clipped to it when drawn.

### Gestures around the writing engine (wave 0.6)
- The stroke pipeline is untouched; gestures only route or observe input. `view/gesture-input.ts` listens (never stops) to the stage's pointer events.
- **Finger taps** (`ink/finger-taps.ts`): `FingerTapDetector` follows the touch contacts of one series (landing within 150 ms, ≤ 12 px movement per finger, lifting within 150 ms, ≤ 350 ms in all); 2 fingers → undo, 3 → redo (`tapActionFor`, setting `tapGestures`). Touches the writing engine would not treat as fingers (pen recently active, palm size, edge zone) or a pen contact in the series make it invalid. At the tap the view snapshot taken at the first landing is restored, then undo / redo runs. In `PointerController` a touch that lands while other touches navigate joins them instead of starting a stroke.
- **Scribble** (`ink/scribble.ts`): at pen-up, before a pen stroke is committed (`NotebookView.eraseByScribble`), the stroke is resampled every 2 pt, turn-backs are found (angle > 120° over 8 pt on each side), and the longest run of legs ≥ 12 pt is checked: ≥ 4 reversals, legs within 45° of a common axis, drift across the axis ≤ 0.8 of the mean leg, ≤ 300 ms per leg, box ≤ 320 pt, ≥ 60 % of the stroke is the scratch. Victims are the strokes crossed by ≥ 2 legs (not larger than 4× the scribble's diagonal); they go in one `removeStrokes` batch and the wet ink is cancelled, so the scribble never reaches the document. No victims → the stroke is kept as ink.
- **Auto-scroll** (`ink/auto-scroll.ts`, `AutoScroller` with an injected clock): `strokeEnded(tipY)` schedules a scroll after 700 ms when the tip is in the bottom 18 %; every frame re-checks that no contact is active; a pointer down or wheel cancels it.
- **Pen side button**: `PenButtonAction` also has `lasso` and `lastTool`. `InputPolicy.penHeldTool` names the tool; `PointerController` passes it to `drawStart(sample, eraser, held)`; the view resolves `last` with `LastTool` (`ink/last-tool.ts`).

### Words and lines (no OCR)
- **Segmentation** (`ink/words.ts`, pure, no `obsidian`): `segmentText(strokes)` returns a `TextLayout`: `lines` (top to bottom) of `words` (left to right) of stroke ids, each with a point-box (`bounds`, no pen-width padding), plus per line a `baseline` (endpoints and slope) and the median `letterHeight`; `ignored` lists strokes that are not handwriting text. This is the foundation for reflow (#92), alignment (#93) and headings (#102): they read the layout and never re-derive it.
- **Method.** Only `pen` strokes count (highlighter and shape strokes are ignored, as are strokes whose larger side exceeds 8× the page's median stroke size). Strokes sorted left to right join the open line whose recent strokes predict their vertical position (centres, not extents, so descenders and ascenders of neighbouring lines may overlap; a short robust slope estimate handles slanted writing; dots, commas and hyphens are matched by their centre with a wider tolerance) and that ends within 5 letter heights to their left, otherwise they start a line (so columns stay apart). Each line's baseline is fitted through the stroke bottoms with a RANSAC over pairs, so descenders do not tilt it. Along the baseline, a gap wider than 0.45× the line's median letter height starts a new word. Everything is relative to the handwriting size; nothing is in absolute pt. Tunable through `TextOptions`.
- **Cost and caching.** Roughly linear in the number of strokes (open lines are kept sorted by y, so a stroke only looks at nearby lines); per-stroke boxes are cached in a `WeakMap`. `TextLayoutCache` keeps the layout of one page and returns it while the stroke objects are the same (O(n) pointer comparisons); the view creates one per `Page` lazily, only when a double tap happens, so writing never pays for it. `npm run bench` (`tests/words.perf.ts`) prints figures for 1,000 / 3,000 / 10,000 strokes.
- **Gesture** (lasso tool only; `ink/multitap.ts`, `view/notebook-view.ts` `selectByTaps`). A lasso-tool contact that moves less than 8 CSS px is a tap; taps within 400 ms and 30 CSS px of the previous one count up (1, 2, 3). Tap 2 selects `wordAt` (the word with a stroke nearest the point, within 12 CSS px), tap 3 `lineAt` (the line of that word, or the nearest line box). It also works when the tap lands inside the previous selection (that would otherwise start a move); a single tap behaves as before (picks the element under it). The lasso tool was chosen over the pen because it never writes: with the pen, a double tap would leave dots and the first tap of the series would already be a stroke to undo. Pan, zoom, palm rejection and the text, shape and pen paths are untouched.
- Known limits: handwriting with very wide letter spacing may split into several words and tightly spaced words may merge (the gap threshold is relative to the line, not learned from the page); text written over a drawing may be grouped with it; rotated pages of text are not detected (lines are near-horizontal, slopes up to about 35°).

### Objects, pages and the navigator
- **Shape tool** (`shapes.ts`): drag out a line, arrow, rectangle or ellipse; points are generated every 3 pt along the outline and stored as a `shape` stroke (constant width, pressure 0.5). `constrain` offers 15° angle snapping for lines and arrows and equal sides for rectangles and ellipses (a modifier key). **Recognition** (`recognize.ts`): after the pen is still for 600 ms (radius 4 px, `isHold`), the stroke is fitted as a line, arrow, rectangle or ellipse and replaced by the clean shape if the fit is good enough; otherwise it stays as written.
- **Text boxes** (`TextElement`) and **images** (`ImageElement`) are page elements, drawn above the background and below the ink. Layout and measurement are shared (`text-layout.ts`); the text box is edited in place (`view/text-editor.ts`). Inserting an image stores the file as an asset and adds the element in one `Batch` (`AddAsset` + `AddElement`) and selects it. The lasso selects strokes and elements together (`elementsInLasso`); a transform is baked into new elements with `ReplaceElement`, deletion is `RemoveElement`, both inside the same `Batch` as the stroke changes.
- **Ruler** (`ruler.ts`, `view/ruler-gesture.ts`): placed by two fingers (centre and angle from the two touches, 20 cm long); pen points within a snap distance of the edge are projected onto it (`projectToRuler`), so a stroke started on the edge stays on the edge; the ruler draws mm/cm ticks.
- **Infinite pages** (`infinite.ts`): when ink reaches the bottom fifth of an infinite page its height grows by half a page of its width, up to 20 times the width; the growth is part of the same undo step (`SetPageInfinite` for the flag, the growth as a `SetPageSize` inside the stroke's `Batch`).
- **Selective eraser** (`erase-filter.ts`): the toolbar state `eraserFilter` (`all`, `highlighter`, `pen`, `color` + `eraserColor`) decides which strokes the eraser may hit; `pen` means every stroke that is not a highlighter (shapes included). Applied before the hit test, so it works with whole-stroke, segment and area erasing.
- **Erase area** (`erase-area.ts`, eraser mode `area`): the outline is drawn like a lasso; on lift every stroke with a point inside is cut at the outline (the outside runs keep their style and get new ids; runs under 2 points are dropped) and text boxes and images whose centre is inside are removed when the setting is on and the filter is *All ink*. One `Batch`.
- **Insert or remove space** (`space.ts`, `model/page-content.ts`, tool `space`): the pages are treated as stacked without gaps from the page touched. Items whose centre is below the line, and all items of the following pages, move by the dragged distance; each lands on the page that contains its new centre (pages are appended, like the last page, when it falls past the end). Removing is limited to the empty gap between what stays and what moves. Pages with a PDF or image background are barriers: the cascade runs only over plain pages, a background page never gets content from another page nor gives any up (overflow from it, or from the plain page before it, goes to a new blank page inserted right next to it, and removing never pulls content across it). An infinite page also ends the cascade and grows. `analyseSpace` decides the moves and is shared by the live preview (`Renderer.setSpacePreview`: the moving content is drawn shifted on the live layer and hidden from the static layer, like a floating selection, by the clamped amount; content that falls on a page that does not exist yet is only hidden) and by `planSpaceChange`. The result is a list of per-page content changes applied by `SetPageContent` (arrays changed in place, previous arrays kept for undo) plus `InsertPages`, in one `Batch`. Nothing in the document format changes.
- **Automatic next page** (`auto-page.ts`): when a committed stroke reaches the bottom tenth of the last page (setting `autoNextPage`, default on; not for infinite pages or pages with a background) an `AddPage` joins the same `Batch` as the stroke.
- **Page navigator** (`view/navigator.ts`): side panel of page thumbnails rendered with the thumbnail code; tap to jump, press and hold then drag to reorder (`MovePage`), star to bookmark (`SetMeta`, `meta.bookmarks`), filter to bookmarked pages. Thumbnails are not refreshed while the pen writes.
- **Insertion**: `InsertPages` adds several pages in one step (PDF range, scanned sheets, blank pages, an image page).

### Benchmarks
- `npm run bench` (`vitest run --project perf --silent=false`): `tests/model.perf.ts`, a custom timing loop (not vitest's bench API) over `stressDocument(10_000, 10)`: serialize, open (parse + validate), open plus first save with a cold cache, next saves, eraser hit test, segment cut, lasso, stroke outline. It is excluded from `npm test`. Dev-PC reference (Windows, Node 24; 10,000 strokes, 10 pages, 6.69 MB): serialize 153 ms; open 227 ms; open + first save, cold cache, 424 ms in total; next saves 16–19 ms; eraser hit test 0.04 ms per move (1,000 strokes, cached bounds); segment cut 0.005 ms; lasso over a quarter page 2.4 ms; stroke outline 0.04 ms. **These are PC numbers**: Android will be slower and must be measured with the in-app benchmark.
- In-app command **Run performance benchmark** (`view/benchmark.ts`): generates the same notebook, then times serialization, the first and later save checks and parse, and renders it with an **off-screen** `Renderer` at the current view size: first draw (builds paths), 30 redraws at fit width, 150 scroll frames, 30 redraws at 3× zoom. It also times the eraser hit test and segment cuts and reports the JS heap where the WebView exposes it. Then the **writing replay** (`ink/writing-bench.ts`): static redraw of a page with 2,000 strokes in render 1 and render 2 (JavaScript time, and with rasterization forced by reading one pixel back), then 10 synthetic strokes of 1.5 s at 120 and 240 Hz written on that page through the old pipeline (frame-aligned events, EMA stabilizer, whole outline rebuilt each frame on the live canvas) and the new one (one event per sample, wet ink painted in the handler): work per sample, per-frame cost, an input→paint estimate (old: half-frame alignment wait + frame work; new: handler work) and the pen-up commit. Nothing is written to the vault; the results can be copied.
- Writing replay on the dev PC (Chromium 152 in the desktop app's browser pane, 1280×800 @2x, off-screen): static redraw of 2,000 strokes with rasterization ≈ 60 ms for both render 1 and render 2 (JavaScript ≈ 1 ms); old pipeline 0.2 ms per frame and an input→paint estimate of 8.5 ms on average (p95 13–15 ms), almost all of it the wait for the frame-aligned event; new pipeline 0.03 ms per sample (p95 0.1 ms), nothing per frame; pen-up commit 0.3–0.6 ms (old 0.4–0.5 ms). `npm run bench` adds: perfect-freehand outline of a stored stroke 0.044 ms vs 0.006 ms for the wet-ink path of the same points; 360 samples through the 1€ filter 0.008 ms (old EMA 0.002 ms); wet-ink geometry for 360 samples 0.03 ms vs 11.4 ms for the old per-frame outlines. **None of this is display latency**, and the PC is much faster than a tablet: Android must be measured with the in-app benchmark and the overlay.
- Command **Create stress-test notebook**: writes the generated notebook (10,000 strokes, 10 pages) to the notebooks folder and opens it, to test real interaction on the device. The in-app benchmark does not measure real input latency; the performance overlay does, in the software sense above.

## 7. Undo/redo

Command stack, not snapshots. Each command knows how to apply and undo itself; a new command clears the redo stack; maximum 500 commands. The history lives in memory (it is not saved in the file) and is reset on reopening or on reload after an external modification.

| Command | Used for |
|---|---|
| `AddStroke { pageId, stroke, index }` | pen and highlighter strokes |
| `ReplaceStroke { pageId, before, after[], index }` | segment erase (cut), whole-stroke erase (`after` empty), transforms, delete selection |
| `AddPage { page, index }` | add or duplicate a page; undoing never removes the last page; applying it twice never inserts the page twice |
| `DeletePage { page, index }` | delete page; a no-op (and so is its undo) on the only page |
| `MovePage { pageId, from, to }` | move up/down; undo puts the page back at the exact position it moved from |
| `SetPaper { pageId, before, after }` | change paper kind and spacing; strokes untouched |
| `SetPageSize { pageId, before, after }` | change page size / orientation; strokes untouched. v6: on a page with margins the background keeps its box and the right/bottom margins take the change (an infinite PDF page grows below the PDF); undo restores the previous margins |
| `SetPageMargins { pageId, before, after }` | v6 page margins: the page grows or shrinks by the change, the background keeps its size; a change of the left margin moves every stroke and element of the page by the same amount (same ids, new frozen objects), so ink never moves relative to the PDF. Undo restores the same objects and the exact previous size |
| `SetPageBackground { pageId, background, size }` | switches a page to another PDF page (a re-published slide) and size; ink, elements and margins stay; undo restores background and size |
| `AddElement { pageId, element, index }` / `RemoveElement` / `ReplaceElement { pageId, before, after }` | text boxes and images: insert, delete, move/scale/rotate/edit |
| `SetMeta { before, after }` | tags, favourite, cover, bookmarks (the library applies it to an open notebook through the view; a closed notebook is rewritten by patching its JSON) |
| `AddAsset { asset }` | registers a PDF or image asset in the document |
| `InsertPages { pages, index }` | several pages at once (PDF range, scanned sheets, image page) |
| `SetPageInfinite { pageId, before, after }` | the infinite-page flag |
| `Batch { label, commands }` | one gesture or action made of several commands (eraser gesture, transform, delete); undone in reverse order |
| `EraseStrokes { pageId, items }` | multi-stroke whole erase from M1; kept and tested, no longer used by the view |

Committed strokes are immutable, so commands refer to stroke objects and indices, never to data that can change underneath them.

## 8. Export (PDF and SVG)

Export reads the document and does not go through the history. Files are written with the Vault API next to the notebook (`<name>.pdf`; single pages `<name> p3.pdf` and `<name> p3.svg`), adding ` 2`, ` 3`… if the name is taken; a notice shows the path or the error. The generators are pure functions in `ink/` (no `obsidian`, no DOM), so they run in tests. Entry points: the page menu (page as PDF, notebook as PDF, page as SVG) and the command **Export notebook as PDF**. Both formats always include the paper pattern.

Both exporters reuse `paperPattern`, the render-aware stroke geometry of the renderer (perfect-freehand polygon for render 1, the committed disc-chain path for render 2) and the same colours, so ink has the same geometry as on screen. Strokes stay vector.

**Images.** Before writing, `view/export.ts` rasterises what the writers cannot draw: each PDF page background is rendered at 200 dpi and each image (asset or scan) is re-encoded, all as JPEG; the same asset used on several pages is embedded once. The PDF writer embeds them as `DCTDecode` image XObjects below (backgrounds) or between (images, with rotation) the paper, text and ink; the SVG writer uses `<image>` with a data URL. An image that cannot be loaded is skipped and a notice says how many. Text boxes are written with Helvetica metrics (`pdf/helvetica.ts`) in the PDF and as `<text>` in the SVG.

**PDF** (`pagesToPdf`, PDF 1.4, written by hand, no library):
- One PDF page per notebook page. **Units: the PDF user unit is 1/72 inch = 1 pt = our document unit**, so `MediaBox` is `[0 0 width height]` with no scaling.
- Objects: 1 catalog, 2 page tree, 3 info (`Producer`, and `Title` = notebook name), then a page object and a content stream per page. The classic `xref` table is built from real byte offsets. Everything is ASCII (the title is a literal string when it is printable ASCII, otherwise UTF-16BE hex with a BOM), so string length equals byte length and the offsets are exact.
- **y-flip.** PDF has its origin at the bottom left, the document at the top left. Each content stream starts with `1 0 0 -1 0 H cm`, so coordinates are written as they are in the document.
- Content: white page rectangle, paper (lines per kind with width and colour via `w` and `RG`; dots as tiny filled squares, to avoid four Béziers per dot), then the strokes in order.
- **Strokes as cubics.** `strokeOutline` returns a polygon; the screen draws it as a chain of quadratic curves (control point = vertex, end point = midpoint to the next vertex). PDF paths have only cubics, so each quadratic is raised exactly: `c1 = p0 + 2/3 (q − p0)`, `c2 = p + 2/3 (q − p)`. The shape is the same as on screen. Each stroke is one closed filled path.
- **Highlighter.** Pages that contain a highlighter stroke declare `/GS1 << /ca 0.35 /BM /Multiply >>` in their resources, and highlighter strokes are wrapped in `q /GS1 gs … Q`: same alpha and multiply blending as the canvas.
- Numbers have at most 2 decimals and never use exponent notation.
- **No compression.** Content streams are not Flate-compressed: no dependency, and the file can be read and checked by eye. The price is size, roughly 100–200 bytes per stroke point, so a page with a lot of ink is several times larger than the same page from a compressing PDF producer. Compression can be added later without changing the structure.

**SVG** (`pageToSvg`): one standalone file per page. `width` and `height` are in mm (it prints at real size), the `viewBox` is in pt. White background rectangle, one path per paper line kind, one path for all dots (circles), one path per stroke; the highlighter has `fill-opacity` 0.35 and `mix-blend-mode: multiply`. The output is deterministic (no ids, dates or random values) and attribute values are escaped.

**What was and was not checked.** Unit tests cover the PDF structure (header and trailer, one page object per page, `xref` offsets and `startxref`, `/Length`, MediaBox, y-flip, colours, ExtGState only with a highlighter, paper on/off, title escaping, two decimals) and the SVG (size, paper, highlighter, escaping, determinism). Beyond the unit tests, an exported PDF was parsed with pdf.js (3 pages, Unicode title, fills, stroked paper lines, highlighter ExtGState) and an exported SVG was rendered with resvg. **Neither was opened on Android**, and how the device displays or shares the files is untested.

## 9. Library

Samsung-Notes-like screen (`library/library-view.ts`) opened from the ribbon or the command **Open library**. Library folders are real folders under the notebooks folder (reserved: `_assets`, `_backup`, `_trash`, `_templates`); a notebook is one file; moving, renaming and syncing work with any tool. The vault is the source of truth.

- **Index** (`library/index.ts`, `library/host.ts`): a cache `library-index.json` in the plugin folder (`INDEX_VERSION` 2). One entry per notebook: path, folder, name, file mtime and size, created/modified, page count, tags, favourite, cover colour, text of the text boxes (capped at 20,000 characters, with the offset where each page's text starts, for the page jump of a search hit) and the first-page thumbnail (a data URL, with the mtime it was drawn from). An entry is stale when the file's mtime or size differs; only stale or new files are read (`filesToRead`), a few at a time, with progress shown in the library ("Indexing…"). Deleting the index only costs a rebuild.
- **Queries**: scope (all, favourites, recent = the 20 last modified, a folder, a tag), search and sort (modified, name, created). Search ignores case and accents, matches title, tags and text, and returns a snippet and the page of the first text hit; the scopes *Everywhere*, *This folder* and *This view* narrow it.
- **Metadata** (tags, favourite, cover) lives in the notebook (`meta`). The host changes it with `patchNotebookMeta` on the document JSON, or through the open session when the notebook is open (so it is saved with the checked path and is undoable there); if the notebook is open and refuses the change the user is told. Duplicating a notebook copies the file and gives it a new document id (`patchNotebookId`), so the journal and version history of the two never mix.
- **Operations**: create (notebook, folder), rename, move (menu or long-press drag onto a folder), duplicate, delete (moves to the library trash, see "Library trash, page trash and templates" below; folders move whole), import a PDF, scan into a new notebook.
- **Thumbnails** (`library/thumbnail.ts`): paper, page background (PDF page or image, loaded through the media source), elements and ink of the first page, drawn on an off-screen canvas; strokes thinner than a minimum are widened so handwriting stays visible, and drawing stops after a time budget.

### Class timetable (roadmap 115)

`src/timetable/`, no document format change. **File**: `<notebooks folder>/_timetable.json`, plain JSON chosen over a Markdown table because it round-trips exactly, is easy to edit by hand and syncs like any file: `{ "version": 1, "weekOne": "YYYY-MM-DD"?, "entries": [{ "id", "course", "day" (1 = Monday ... 7), "start" "HH:MM", "end" "HH:MM", "room"?, "notebook"? (notebook path or course folder), "weeks": "all" | "odd" | "even", "from"?, "to"? }] }`. `parseTimetable` is strict: anything it cannot understand is an error and the file is left alone (the editor says so and offers to start a new timetable, copying the old file to `_backup/` first); saves are serialized, re-parsed and compared, written with `vault.process`, then read back. Only the Vault API is used.

**Logic** (`schedule.ts`, pure, tested): local wall-clock time (`Date` getters), end exclusive; alternating weeks count from the week containing `weekOne` (week 1 is odd), else ISO week numbers; `from`/`to` are inclusive; `classesAt(now, lead)` counts a class from `lead` minutes before it starts, overlapping classes: the one started last is current; `nextClass`, `findOverlaps`, `courseForNotebook`, `pickTarget` (linked file, else a folder's notebook named like the course, else its latest, else a new notebook).

**Runtime** (`service.ts`): `TimetableService` reloads on file change, registers a course provider (`current.ts`) that `runNewLecture` asks for the default course, offers the class in progress on layout ready and when the library opens (once per class and day per session; a notice with a button, or directly with *Open it without asking*), and `openClass` opens the notebook, waits for its edit context and adds the lecture page with `addLecturePage` (shared with New lecture), or shows the existing one. The library host exposes `nowClass()` for the *Now: <course>* shortcut.

**Page tag hook**: `applyCourseTag(page, course)` in `page-tag.ts` is called for lecture pages created with a known course and currently returns the page unchanged. Once page tags exist in the format, implement that function only and set `PAGE_TAG_HOOK_ACTIVE`.
### Library trash, page trash and templates (wave 0.6; #160, #26, #74)

No change to the document format. All three live in plugin-owned folders under the notebooks folder, reserved like `_assets` and `_backup` (`RESERVED_FOLDERS`: `_trash`, `_templates`), so the library tree, index, search, companion notes and conflicted-copy detection never see them (`isInTrash` in `storage/trash-paths.ts` is the root-independent test used outside the library).

- **Library trash** (`storage/trash-paths.ts` pure, `storage/trash.ts`, `library/trash-modal.ts`). Deleting a notebook or folder from the library moves it with `vault.rename` (links in the user notes are not rewritten) to `_trash/items/<id>/<original name>` and writes `_trash/items/<id>/meta.json` first (`kind`, `name`, `originalPath`, `deletedAt`). One folder per item, so items never collide, a trashed notebook has no sibling to be taken for a conflicted copy, and nothing is renamed on the way in. Open tabs that show the item are closed first so they flush. A non-empty folder can now be deleted: it moves whole. Restore moves the item back to `originalPath`, creating missing parent folders, or to the same name with " 2", " 3"... when the path (compared without regard to case) is taken (`restorePath`). Permanent deletion and Empty trash ask for confirmation and go through `fileManager.trashFile`, so Obsidian's own *Deleted files* setting decides what happens to them. A meta file that cannot be read, or an item that is not where the meta says, is left alone and not listed. Setting `trashRetentionDays` (default 0 = never) empties items older than that many days when Obsidian starts (`expiredIds`). The trash view is a dialog opened from the *Trash* entry of the library sidebar.
- **Assets.** Nothing deletes files in `_assets/` today (there is no library check yet, #27), so assets used only by trashed notebooks or deleted pages stay. When a clean-up of `_assets/` is written it must treat the notebooks in `_trash/items/` and the assets listed in `_trash/pages/` (`trashedAssetIds`) as references.
- **Page trash** (`model/page-trash.ts` pure, `storage/page-trash-store.ts`, `view/page-tools.ts`). *Delete page* first writes the page to `_trash/pages/<notebook id>.json`: `{ format: "obsidian-notebook-page-trash", version: 1, notebookId, entries: [{ id, deletedAt, index, afterPageId, document }] }`, where `document` is a one-page notebook document (validated and migrated by the normal reader) carrying the asset records the page needs; the asset files stay in `_assets/` and are referenced by id. Writes of one notebook are queued; a file that cannot be read is renamed aside (`<id> (unreadable <time>).json`), never overwritten. Retention: the 50 most recent pages per notebook, none older than 30 days, applied on each deletion (`PAGE_TRASH_MAX_ENTRIES`, `PAGE_TRASH_RETENTION_DAYS`); deleting the same page again replaces its entry. *Deleted pages...* in the page menu lists the entries whose page is not in the notebook (so an undone delete does not show up) with thumbnails; *Restore* is one undo step (asset records added back, the page keeps its ids unless the notebook already uses one) and inserts after the page that preceded it if that page still exists, else at the old position clamped. A restored entry stays in the file until the retention drops it; it is hidden while its page is in the notebook and shows again if the restore is undone.
- **Templates** (`model/templates.ts` pure, `storage/templates-store.ts`, `view/page-tools.ts`). A template is a normal one-page notebook file in the templates folder (setting `templatesFolder`, default `<notebooks folder>/_templates`): content, paper, size and background of the saved page, with new ids. *Save page as template...* writes it (validated); *New page from template...* (page menu) and the template row of the *New notebook* dialog open a gallery with thumbnails of the built-in templates (Cornell, meeting notes, to-do list; generated in code, translated labels passed in) and of the stored ones (which can be deleted from the gallery, through Obsidian's trash). Using a template always copies the page with fresh ids; a new page is one undo step.


## 10. PDFs, images and assets

- **Assets**: PDFs and images are copied into `<notebooks folder>/_assets/<id>.<ext>`, where `id` is the first 24 hex characters of the SHA-256 of the content (`pdf/hash.ts`). The same file imported twice is stored once. The notebook only holds `assets[id] = { id, kind, path, name, bytes }`. Saving a notebook with a long PDF writes only ink. `resolveAssetFile` finds the file by the stored path, then by the content-addressed name in the current `_assets` folder. Missing assets give a placeholder (file name) and the ink is kept; the document is not changed. The save check verifies that every page background and image element refers to an asset of the right kind, and the stored asset is checked when added.
- **PDF engine** (`pdf/pdf-store.ts`, pure with injected `loadPdfJs`, `readAsset` and `createCanvas`): pdf.js comes from Obsidian's `loadPdfJs()`, no bundled copy. At most 3 documents stay open (LRU, destroyed on eviction, never while busy); rendered bitmaps live in an LRU bounded by a memory budget (160 MB by default; the most recent one is always kept); the scale is clamped so neither side exceeds 4096 px; renders are cancellable; while zooming, the previous bitmap is scaled until the sharp one arrives (`peek`).
- **Import as notebook** (`library/import-pdf.ts`): reads the page sizes, builds one page per PDF page (page size = PDF page size, `background: { kind: "pdf", asset, page }`, no paper pattern), writes the notebook and opens it; a PDF of 1 MB or more shows a progress notice while its pages are measured (`LARGE_PDF_BYTES`). **Insert** (`InsertPages`) adds a range or the whole file after the current page; a blank page or an image page can be inserted anywhere.
- **Lecture pack (#191, #192, #193)**: `model/lecture-pack.ts` turns slide sizes into a page plan with no format change. Layout `slide` = one page per slide at the PDF size on blank paper (as *Import PDF* always did); `notes-right` / `notes-bottom` = one slide per page, the slide scaled so that its longer side is 640 pt (the handwriting scale is then the same for every course), the page grown by a right margin of 0.6 × the slide width or a bottom margin of 0.8 × the slide height (`PageMargins`, v6) and given the chosen paper, which shows in the margin because the background covers only its box. *Notes page after every slide* adds a blank page with the same size (margins included) and the chosen paper after each slide page. `library/lecture-pack.ts` builds the notebook (a header page copying the size and paper of the first slide page, or a header text box in the notes area of the first slide page, or no header; the header text is the one of *New lecture*) and runs the flow with an injected host: pick the PDF (vault or device) → dialog (course, date, header, layout) → store the PDF as a content-addressed asset → page sizes → `serializeChecked` → create in the course folder → open. *New lecture from slides…* is a command (folder: that of the notebook in view, else the notebooks folder), a library button and a folder menu entry (that folder). *Insert PDF* in the page menu asks the same layout questions after the page range, builds the pages with the same function and inserts them as one `Batch` (`AddAsset` + `InsertPages`). *Exercise page here* (`exercisePage`, page menu / toolbar … menu / command) inserts a blank page of the full size of the current page with the paper shared with *notes page after every slide* (one `AddPage`). The last layout is remembered on the device (Obsidian local storage, never in the vault). **Two or three slides per page need a format change and are not implemented**: a page has exactly one `background` (one PDF page). Drawing the extra slides as image elements would rasterise them (blurry when zoomed, no text for search, re-publishing or annotation export), so the proper fix is a page field with several backgrounds, each with its own box (a v7 candidate; the margins already provide the notes area).
- **Export** is described in §8: backgrounds and images become JPEG (PDF pages at 200 dpi). A page with margins is exported at its full size with the PDF in its box (`backgroundRect`), like the screen and the thumbnails.
- **Margins (#104)**: page menu *Page margins…* (or the command) on a page with a background asks left, right and bottom in mm (a right margin of half the PDF width is suggested), optionally for every page of the same PDF, and applies `SetPageMargins` as one undo step. Format: §2 (v6).
- **Re-published slides (#235)**: page menu *Update PDF from a new version…* (or the command). The chosen file is read in a temporary `PdfStore` (it is stored in `_assets` only when the update is applied). Each page of the new PDF and each distinct PDF page of the notebook gets a fingerprint (`pdf/republish.ts`): its pdf.js text, normalised; pages with fewer than 24 characters of text also get a 64-bit difference hash of a ~72 px rendering. Matching: (1) equal fingerprints are the same slide, *unchanged*, one to one, closest page number first, whatever the order; (2) "that PDF" is the asset of the page in view plus every asset with at least 3 unchanged pages or more than half of its slides unchanged (one shared "Thank you / Questions" slide does not pull in another lecture), and step 1 is repeated with those slides only; (3) remaining new pages are *updated* versions of remaining slides of that PDF when their words overlap enough (Dice ≥ 0.5 after removing words found on more than half of the pages, such as footers) or their image hashes differ by at most 10 bits; (4) the rest is *new*. A summary (new, updated, unchanged, not in the new version) lets the user switch each updated slide or keep the old one; each updated slide names the PDF it comes from, and only slides of the main asset (the one in view) start switched on. Applying is one `Batch`: `AddAsset`, `InsertPages` of the new pages after the last page of that PDF (and the blank note pages after it), with that page's margins, and `SetPageBackground` for every notebook page that shows an accepted updated slide (an infinite page never gets shorter: with margins the extra height goes into the bottom margin, `SetPageMargins`). Unchanged pages keep pointing at the old asset; old assets are never removed.
- **Synchronised PDF ↔ notes view (#106)**: command *Open PDF side by side* (and the same entry in the "…" page menu; *Close*, *Link this page to the slide in view*, *Add notes page for this slide* once open). Use cases: (a) a plain `.pdf` of the vault, read-only, rendered by a separate `PdfStore` (not stored in `_assets`); (b) another notebook, shown page by page with its PDF backgrounds and ink, read-only. **Split: inside the notebook view, not a second Obsidian leaf.** Obsidian on phones and tablets has no split panes in the main area (a split opens a tab), so only an internal split works on every device, and the controller can talk to both sides directly. The pane is inserted into `.notebook-body` before the page navigator and the stage; the stage keeps its own resize handling, so the notes refit as the divider moves. Layout (`pdf/sync-layout.ts`): side by side when the view is at least 700 px wide and clearly landscape (tablet held sideways, desktop), stacked otherwise (phone, tablet upright); a draggable divider keeps 20-80 %. The pane shows one reference page at a time, fitted to its width (scrolls if taller), so it does not depend on the notes view's scroll mode: the notes side follows through the view's current page whichever way it scrolls.
  - **Links**: the notebook format has no field for them (no format change), so they live in a sidecar, `<config dir>/plugins/<plugin id>/pdf-links.json`: `{ format: "obsidian-notebook-pdf-links", version: 1, links: [{ notebook, page, source, pdfPage, path? }] }`, one link per line. `notebook` is the notes document id, `page` the notes page id, `source` the content id of the PDF (first 24 hex of its SHA-256, the same id a notebook uses for the asset, so renaming or moving the file does not matter and a PDF imported as a notebook asset keeps its links), `pdfPage` the 1-based page, `path` a hint for plain vault PDFs (a file replaced in place by a new version is still recognised by its path). A notes page has at most one link; several notes pages may share a PDF page. The file is written only by explicit actions (*Link*, *Unlink*, *Add notes page for this slide*), never on scroll or page turn. Each write reads the file again first and applies the operation to what is there (another device may have synced a change), serialises, re-validates and writes only if the text changed; an unreadable file or one from a newer version is never overwritten (one copy `pdf-links.unreadable-<hash>.json` is kept, links are switched off with a message). Entries a version does not understand are written back unchanged. Links to deleted pages are ignored, not removed (so undoing a page delete brings its link back).
  - **Following** (header toggle *Follow*, on by default): turning the PDF page shows the first notes page linked to it, unless the page in view already is one; scrolling the notes (after 120 ms) shows the PDF page the notes page in view is linked to, if that PDF is the one beside it. Programmatic moves are not echoed back. A PDF page without a linked notes page shows the strip *Add notes page for this slide*: it inserts a page (size and paper of the page in view) as one undo step, placed in slide order (after the last page linked to this PDF at or before that slide, otherwise before the first linked to a later slide, otherwise after the page in view), and links it. If the notes are elsewhere than the linked page, the strip offers *Show*. The reference pane is not remembered across restarts.
- **Annotation export (#155)**: page menu or command *Export PDF annotations to Markdown*. For every PDF page: each highlighter stroke (with the PDF text under it: pdf.js text runs are split into equal-width character cells, and a cell whose middle lies within half the stroke width of the stroke's centre line is selected) and each non-empty text box, top to bottom. The note (`<notebook> annotations.md` next to the notebook, ` 2`, ` 3`… if taken: an existing note is never overwritten) has a wikilink to the notebook (`fileManager.generateMarkdownLink`), one section per notebook page and one callout per item with an `obsidian://notebook?…&page=n` link (`integration/links.ts`). PDF text is escaped; text boxes are copied as written. Pages without a text layer (scans) list their highlights without text.

## 11. Scanner

`scan/` turns a photo into a page background; there is no live camera inside the plugin (the photo comes from the system camera through a file input with `capture`, or from a file).

1. Load the photo, downscale to at most 2400 px on the long side.
2. **Detect** (`detect.ts`): downscale to 256 px, find the page quadrilateral (contrast, convex hull of the bright region, area between 15% and 97% of the image, fill ratio); no result means default corners are shown.
3. **Crop**: four draggable corners with a loupe (`scan-modal.ts`); corners are ordered (`orderCorners`).
4. **Warp**: a homography maps the quadrilateral to a rectangle (`geometry.ts`); the output size comes from the edge lengths.
5. **Filter** (`filters.ts`): *Original*, *Document* (pixels clearly darker than their surroundings become black, the rest white, with a short soft ramp) and *Whiteboard*; rotate; the preview uses a smaller size than the final output.
6. The result is encoded as JPEG, stored as an image asset and becomes a page with `background: { kind: "image" }` (`scan/pages.ts`, page size from the aspect ratio), inserted with `InsertPages` after the current page, or as an image element (**Insert scan as image**), or as the pages of a new notebook (library, command). Several sheets can follow one another in one session.

## 12. Obsidian integration

`integration/` registers the parts that talk to Markdown notes and the app (called once from `onload`):
- **Embeds** (`embed.ts`, `links.ts`): the code block language `notebook`. Source forms: `path: Notebooks/Physics.notebook` with an optional `page: 3`, a bare path with `#3` / `#p3` / `#page=3`, or a wikilink `[[Physics#p3]]` (resolved relative to the note with Obsidian's link resolution, then by file name in the notebooks folder). The path may omit the extension. The block renders one page with the thumbnail code at the width of the note (device pixels capped at 2048), is static (no editing), redraws 400 ms after the notebook changes (modify, rename, delete, create), and a click opens the notebook at that page. Errors (empty block, bad page, not found, page out of range, unreadable) are shown in the block. The command **Insert notebook embed** writes the block at the cursor.
- **Protocol** (`protocol.ts`): `obsidian://notebook?path=<vault path>&page=<n>` (`vault=<name>` is handled by Obsidian). It opens the notebook, reusing the open tab, and scrolls to the page.
- **Opening at a page** (`open.ts`): library search hits, embeds and links go through `openNotebookAtPage`, which opens the file and gives the view `{ page }` as state; a view that is already open is told to scroll.
- **Version history** (§4): `history-service.ts` registers the snapshot hooks and the restore command.
- **Companion notes (O1)**: see below. Without them (the default) notebooks stay invisible to Obsidian's own search, tags, backlinks and graph.

### Companion notes (O1)

A Markdown note per notebook so that Obsidian's search, graph, tags, Dataview and Bases see notebooks. **Off by default** (setting *Companion notes*): turning it on creates files in the user's vault (one per notebook, synced to every device), which should never happen as a side effect of an update, and the notes only help people who use those Obsidian features. When on, a note is created the first time a notebook is opened or changed; *Update companion notes of all notebooks* (command, and a button in the settings) does the rest at once.

**Three layers**, so M4 can reuse the content:
- `model/companion-content.ts` (pure): `companionContent(doc, { notebookPath, pageUri })` → `{ properties, tags, text }`; `renderRegion()` wraps the text in markers; `mergeRegion()` and `mergeProperties()` apply it to a note that may have been edited. The output depends only on the document and the notebook path: no clock, time zone, UI language or vault name, so two synced devices produce byte-identical notes.
- `storage/companion-path.ts` (pure): settings (`companionNotes`, `companionLocation` = `beside` | `folder`, `companionFolder`, `companionName` with `{name}`) and `companionPath()`. In folder mode the notebook's folder relative to the notebooks folder is mirrored, so equal names in different folders do not collide.
- `integration/companion.ts`: when to write, which note is the companion, and the Vault calls.

**Content.** Plugin-owned properties, in order: `notebook` (`[[<vault path>|<name>]]`, a real link: the graph and backlinks see it), `notebook-id` (the document id: how the plugin recognises its notes), `pages`, `created`, `modified` (UTC, minute precision, `2026-10-29T14:42:00Z`: identical on every device, and an ink-only save changes the note at most once a minute), then every field of `meta` with a string, number, boolean or list value under its own name (`favorite`, `cover`, and `course`, `teacher`… when the format adds them), with `bookmarks` as page numbers. `tags` holds the notebook's tags as Obsidian tags (no `#`, spaces → `-`, invalid characters dropped, numeric-only tags left out). The body has one generated region:

```
%% notebook-companion:start (generated by Notebook: edit outside this block) {"v":1,"keys":[…],"tags":[…]} %%
### p. 1
[↗ p. 1](obsidian://notebook?path=Notebooks%2FPhysics.notebook&page=1)

<text boxes of page 1, top to bottom, then left to right>
%% notebook-companion:end %%
```

Only pages with text get a section. The heading is language-neutral (`p. N`), so `[[Physics#p. 3]]` links to that section. The page link has no `vault=` (Obsidian uses the current vault), so it does not change with the vault's name. Text-box text is kept as written (links and inline `#tags` work) except what could break the note: `%%` is escaped, and lines that would open a fence, a math block or an HTML block, or become a heading, a heading underline or a rule, get a leading backslash.

**Ownership** (the user may edit the note):
- Everything outside the region, and every property that is not plugin-owned, belongs to the user and is never changed.
- The region is replaced as a whole. With no region (new note, or the user deleted it) it is appended at the end. If the markers are missing one half, repeated or out of order, the note is not written at all and a notice says why.
- Plugin-owned properties are overwritten from the notebook. Which keys the plugin owns, and which tags it added, is stored on the start marker (`keys`, `tags`), so a key the notebook no longer has (an emptied `course`, cleared bookmarks) is removed, and nothing else. Without a readable state nothing is removed.
- `tags` is shared: notebook tags first, then the user's own; tags the plugin added before and the notebook no longer has are removed.
- The whole note (frontmatter with the merged properties, and the region) is built as text by `updateCompanionText` (pure, `model/companion-content.ts`) and written once with `vault.process` (atomic), so a sync client never sees a half-updated note. The frontmatter block is re-serialized only when a plugin-owned property changed; otherwise it stays byte for byte. If the frontmatter is not valid YAML, or the markers are broken, the note is left alone.

**Which note** (`companionClaim`). The note at the configured path (or `<name> (notebook).md` if a note of the user's already has that name: it is never taken over) when its `notebook` link points at this notebook, or its `notebook-id` is this notebook's and its link resolves to no notebook. Otherwise any note found through the metadata cache whose link points at this notebook, or that has this `notebook-id` and a link that resolves to nothing (the user moved it, the location setting changed, the notebook was renamed outside Obsidian: existing notes are not moved), but the latter only when no other notebook in the vault has the same id: a file copy of a notebook keeps the id, and must not take over the original's note (both would rewrite it back and forth). Otherwise a new note is created at the first free path.

**When.**
- Triggers are the notebook's own events: `modify` (4 s debounce only when the file holds what a view on this device just saved, `DocumentSession.isOwnWrite`; 30 s for every other change, i.e. sync, another app or library actions, also when the notebook is open here, so that the companion written by the other device usually arrives first and the identical content found here causes no write: two devices writing the same note make the sync client create conflicted copies), `file-open` (30 s as well; creates missing notes lazily and writes only if the note differs), `create` (5 s, registered after layout-ready), `rename`, `delete`.
- Never while writing: capture-phase, passive `pointerdown`/`pointerup`/`pointercancel` listeners note activity inside `.notebook-view`; a due update waits until no pointer is down there and 1.5 s have passed (a pointer seen down for 15 s without an up is ignored). The notebook's own saves are already deferred while writing (§4), so the `modify` that starts an update arrives in a pause anyway.
- **No write when nothing changed**: the new frontmatter and body are computed first and compared with the note (a timestamp read back as a Date compares equal); only the parts that differ are written.
- **No loops**: the service never listens to `.md` files (its own writes and the user's edits start nothing) and never writes the notebook, so the notebook view's external-change check is never involved.
- The document comes from the open view when there is one (no second parse), otherwise from the file; an unreadable notebook gets no update.

**Rename and delete.** When a notebook is renamed or moved and its companion is at the configured place for the old path, the companion is renamed to the place for the new path with `fileManager.renameFile` (Obsidian updates links to it); a companion the user put elsewhere stays there. Renaming a folder in `beside` mode moves the companions with it. On **delete the companion is kept**: it may contain the user's own writing, and deleting a notebook from the library only moves it to the trash (restoring it reconnects the companion by id). A notice names the kept note (one notice for a folder of notebooks). Its `notebook` link becomes unresolved.

**Library and index.** Companion notes are `.md`, which `isNotebookFile` rejects, so the library, the index, the picker and version history never treat them as notebooks. A companion folder placed inside the notebooks folder shows up in the library sidebar as a folder without notebooks.

**Shared tags (O2).** A notebook's tags live in `meta.tags`; Obsidian only indexes Markdown, so they reach the Tags pane and tag search through the companion note's `tags` property (with companion notes off there is nothing for Obsidian to index, and the tag editor says so and offers to turn them on). `model/tags.ts` (pure) is the single definition of a tag: `normalizeTag` writes tags like Obsidian (no `#`, spaces → `-`, `a/b` nested, no empty levels, not only digits; letters, digits, marks, emoji, `_`, `-`, `/` are kept), and the companion generator uses the same function, so what the tag editor stores is what the note gets. The tag editor (`integration/tags.ts`, used by the library menu and by the command *Edit tags of this notebook*) suggests tags from `metadataCache.getTags()` (not in the public typings: feature-detected, with a fallback that counts `getAllTags` over the notes) plus the library's own, ranked prefix, nested level, substring, and refreshes the companion note 2 s after saving. The library filter treats `a` as including `a/b` and counts a nested tag for its parents, like the Tags pane. Merge rule for the `tags` property (`computeSharedTags`): every notebook tag is present; a tag in the note that the plugin did not add is the person's and is never removed (even if the notebook later gets or drops a tag of the same name; their spelling is kept); only tags the plugin added earlier and the notebook no longer has are removed. "Added by the plugin" is the `tags` list on the region's start marker, which now holds only the tags that were not yet in the note when the plugin added them (before 0.6 it held all of the notebook's tags). The notebook is the source of truth for its own tags: deleting one of them from the note by hand brings it back, and a tag added only in the note is not copied into the notebook (one direction only: notebook → note).

**Public API (#168; `docs/api.md`).** `app.plugins.plugins["notebook"].api` (set by `registerIntegration`) exposes `version` (semver of the API), `createNotebook`, `addPages`, `insertImage`, `exportPdf`, `getNotebookInfo`, `openNotebook`, `listNotebooks` and `NotebookApiError`. No format change. Arguments are validated (unknown option names are refused) and every failure is a `NotebookApiError` with a code. An edit is built once as model commands (`Prepare` in `integration/api-plan.ts`) and run in one of two ways: **open notebook** → `NotebookView.editContext()` (waits up to 3 s for a loading view or a pen that is down, then `busy`), one `Batch` = one undo step, `flush()`, then the file is read back and must contain the change; **closed notebook** → `planClosedEdit`: parse, apply the commands to the parsed document, `serializeChecked` (full), verify the change in the parsed result; then backup of the previous text (`before-api`), `vault.process` only if the file still holds what was read (one retry, then `changed-elsewhere`), read back and verify (the same pattern as the closed destination of "Move to notebook…"). An unreadable file never produces text, so it is never overwritten. Calls on one notebook are serialised (`KeyedQueue`). Images are stored with `storeAsset` (content-addressed in `_assets/`) and decoded with `photoSize`; the format of the bytes is recognised from the first bytes. `exportPdf` uses the open view's in-memory document or the parsed file with a fresh `NotebookMedia`, and writes the PDF with the same writer as the UI.

**M4.** If notebooks become `.md` (option B), the notebook file itself gets `companionContent()` as its frontmatter and generated body (the region markers and merge rules stay), the `notebook` property is dropped, and the migration can fold an existing companion into the notebook: its user text and properties are already separated from the generated parts. Links like `[[Physics]]` written against a companion at the default place (`Physics.md` next to `Physics.notebook`) then point at the migrated notebook.

### Zettelkasten (M15 Z1, Z2, Z3, Z11, Z12; wave 0.6)

Cards (Zettel) are ordinary Markdown notes that show a page, or a region of a page, **live**: the note embeds the ink, nothing is copied, so writing in the notebook updates every card. The document format is unchanged: **nothing about cards is stored in the notebook file**.

**Card note.** Created with `vault.create` in the card folder (setting, default `Zettelkasten/`), named `<id> <title>.md` (just `<id>.md` without a title; ` 2`, ` 3`… if taken). Properties, in order: `zettel-id`, `title`, `aliases` (the title), `type` (`permanent` | `literature` | `fleeting`), `source`, `date` (local `YYYY-MM-DD`), `tags`, `notebook` (`[[<vault path>|<name>]]`: the graph shows card → notebook), `notebook-id` (document id), `page-id` (the page's id, never its index), `region` (`x,y,w,h` in page units, absent for a whole-page card). Body: the live embed, then an empty `## Transcription` section (Z11; language-neutral so handwriting recognition can fill it later, M5):

```
![[Notebooks/Box.notebook#p3&id=<page id>&r=40,60,200,120]]

## Transcription
```

**Card subpath** (`zettel/subpath.ts`, used by `links.ts`, `page-links.ts` and `embed.ts`). After `#`: the page part as before (`p3`), then `&`-separated parameters in any order: `id=<page id>` and `r=x,y,w,h` (one decimal). Unknown parameters are ignored, a malformed `id` or `r` is an error shown in the embed. With `id`, the embed shows that page wherever it is now (the `p3` is only a fallback for readers that do not know `id`); if no page has that id the embed says the card's page was deleted and never shows another page. With `r`, the page preview renderer (`library/thumbnail.ts`, option `region`) draws only that part, at the region's own aspect ratio, with the PDF or image background rendered at the matching resolution. Plain `#p3` links behave as before; following a card link opens the notebook at the `p3` page.

**Index.** `ZettelService` keeps an in-memory map of cards built from the metadata cache (`zettel-id` + `notebook-id` + `page-id`), updated on `metadataCache` `changed` and vault `delete`/`rename` of `.md` files. Those events only update the index and redraw overlays; they never write. A note counts as a card of a notebook file when its `notebook-id` is that document's id and its `notebook` link resolves to that file (or to no notebook: moved outside Obsidian), so a file copy of a notebook (same id) does not take over the original's cards. Companion notes skip any note with a `zettel-id` (`companionClaim` would otherwise accept a card, whose `notebook` link and `notebook-id` match).

**Writes** (zero data loss, no sync churn).
- A card is created only on an explicit action (*Make card from selection*, *Make card from this page*, the slip-box commands) or, in a slip-box, after this device's own save added a page.
- After creation the plugin only ever changes three things, each with one `vault.process` that re-serializes the frontmatter block only when a value really changes (`editProperties`; the body is kept byte for byte, invalid YAML leaves the note alone with a notice): `orphaned` (set when the card's page is no longer in its notebook, removed when it is back, e.g. after undo), `links` (drawn links, appended, never removed) and `title`/`aliases` (*Set card title*, explicit). Earlier titles stay in `aliases`. A note still named after its id alone is renamed to `<id> <title>` through `fileManager.renameFile`, so links follow.
- **A card is never deleted** by the plugin. Orphaned cards (page deleted, or notebook not found) are listed by *Show orphaned cards*; *Show cards of this notebook* marks them too.
- Triggers are notebook `modify` events only: 4 s after this device's own save (`DocumentSession.isOwnWrite`), 30 s after any other change (sync, another app: the other device's card writes usually arrive first, and identical values cause no write). Due work waits until no pointer is down in a notebook view and 1.5 s have passed (`InputWatch`, shared with companion notes). Slip-box creation and arrow links run only after own saves, so two devices do not both create the same card.

**Slip-box (Z2).** A notebook is a slip-box when its document id is in the setting `zettelSlipBoxes` (plugin settings, not the notebook file: no format change). *New slip-box* creates a notebook with A6 pages (105 × 148 mm, default paper) and a card for its first page; new pages use the size of the page they follow, so they are A6 too. *Make this notebook a slip-box* creates a card for every page without a whole-page card (asking first when there is more than one). After an own save of a slip-box, every page without a card gets one (at most 20 at a time; a `<doc id>/<page id>` set prevents duplicates while the metadata cache catches up). Limitation: the setting is per device unless the plugin settings are synced; a device that does not know the notebook is a slip-box just does not create cards (the cards created elsewhere arrive by sync).

**Drawn links (Z3).** An arrow drawn with the shape tool (or recognised from a held stroke) is one polyline tail → tip → wing → tip → wing (`ink/shapes.ts`). `arrowEnds` takes the point farthest from the tail as the tip and checks the straight shaft and the out-back-out head; `cardAt` maps each end to the smallest region card containing it (6 pt tolerance), else to the page's whole-page card. Tail and tip on two different cards add a wikilink to the other card to each note's `links` list (`addLinks`, de-duplicated by target), which Obsidian shows in the graph and backlinks. Automatically, only arrows drawn after the notebook was opened in this session are linked (the shape strokes present when the view first had the document are remembered), so a link the user removed from a note is not put back; *Link cards joined by arrows on this page* does every arrow on the page on request. Deleting an arrow does not remove the link.

**Region overlay.** `NotebookView` exposes two small hooks for DOM overlays (`overlayChanged`, called at the end of every `setViewport`, and `overlayGeometry()` with the stage, viewport and page boxes) and `selectionRegion()` (lasso bounds). `zettel/overlay.ts` places one absolutely positioned element per visible card on the stage (`pointer-events: none`, so it never affects input): a dashed outline for region cards and a small id badge (top right; whole-page cards only get the badge). Setting *Show card regions* (on by default) and the command *Show or hide card regions*.

**Z12, the M4 container move.** Everything goes through `storage/format.ts` (`isNotebookFile`, `readNotebookText`) and the document id; cards refer to pages by id, so a migration that keeps document and page ids keeps every card. If notebooks become `.md`, the notebook's own frontmatter will hold `notebook-id` (companion content), but never `zettel-id`, so it is not taken for a card. Obsidian renders `![[X.md#…]]` itself, so the migration rewrites the embed line of card notes (`zettel-id` in frontmatter, line = `cardEmbed()`) to the `notebook` code block form with the same subpath (`path: X.md#p3&id=…&r=…`), which `parseEmbedSource` already reads; the card's properties need no change.
